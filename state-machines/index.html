Moore vs. Mealy, side by side

Same detector, two machines. The circuit you'd wire is different, and so is when the output arrives.

The example: a sequence detector watching a single-bit input stream, one bit per clock, that raises Y whenever it has just seen two consecutive 1s (overlap allowed, so 1 1 1 asserts Y on both the second and third bit). It's small enough to draw completely, and it's the textbook case where Moore needs an extra state that Mealy doesn't.

Mealy — output on the arrow

stateinput=0input=1
S0S0 / 0S1 / 0
S1S0 / 0S1 / 1

Moore — output on the state

stateYinput=0input=1
S00S0S1
S10S0S2
S21S0S2
The extra state is the real cost of Moore here, not a stylistic choice: since Y can only depend on which state you're in, "last two bits were 1" and "last one bit was 1" have to be different states, even though Mealy can tell them apart using the same state plus the current input.

What that costs you in time

Feed both machines the same bit stream, cycle by cycle, off the same clock. This is the part that actually shows up in interviews: Mealy's output reacts within the same cycle the input changes (combinational path from input to output), while Moore's output only updates on the next clock edge, one cycle after the state that causes it.

Bit stream: 0 1 1 0 1 1 1. Mealy's Y (orange) goes high in the same cycle as each qualifying 1; Moore's Y (green) shows the identical shape shifted one full cycle right, because it can only reflect a state the register reached on the previous edge.

Reading the trade-off

Mealy reacts faster and often needs fewer states, but because its output is a combinational function of the input, a glitchy or asynchronous input can glitch Y before the next clock edge cleans it up — a real concern if Y drives something outside the synchronous domain. Moore's output only ever changes on a clock edge, so it's glitch-free and simpler to time-close, at the cost of the extra state (here, one extra state and one extra cycle of latency).

Blueprint: turning a problem into a state machine

This is the order that actually works when you're staring at a blank page in an interview or at your desk. Skipping straight to RTL is where most FSM bugs are born.

1

Pin down the spec in one precise sentence

"Assert Y for one cycle, the cycle after the second consecutive 1, overlaps allowed." Vague specs ("detect two ones") hide the exact bugs that show up later — overlapping vs. non-overlapping, level output vs. one-cycle pulse, what happens on reset mid-sequence. While you're here, check one more thing that's easy to skip: is every input actually synchronous to this block's clock already? If a signal comes from a different clock domain or an off-chip pin (a button, a cable), it needs a synchronizer — and possibly a debounce filter — before it's safe to treat as an FSM input at all. That's a separate problem from the FSM itself (worked example 4 below is entirely about it), but it has to be solved first, not patched in afterward.

2

Find the states by asking what you need to remember

A state is an equivalence class of histories: two different pasts belong in the same state if, for every possible future input, they'd produce identical outputs and land in identical next states. So ask, "what's the minimum fact about everything that already happened that I still need?" For the detector, that fact is just "how long is the current run of 1s" — capped, because once it's ≥2 the exact count stops mattering. That's the whole derivation: states = {run of 0, run of 1, run of ≥2}.

3

Draw it and fill every cell

Every state needs an outgoing transition for every legal input value — no exceptions. A missing transition is either an inferred latch when you get to RTL, or a state diagram that's quietly wrong. If some input combination truly can't happen, route it somewhere safe anyway (see the reset callout below) rather than leaving it undefined. When more than one input can matter at once — two requesters asking in the same cycle, say — "every cell" can mean 2N combinations per state, which stops being literally enumerable past a handful of inputs. The way out is the same one real RTL uses: write the logic as a priority chain (if (req0) … else if (req1) … else …) instead of a flat truth table. An if/else chain with a final else is exhaustive by construction, so it still satisfies "every cell filled" — it's just expressed as a priority, not a list (worked example 5 below is built entirely around this).

4

Minimize — merge rows that are identical

Once the table is complete, scan it: if two states have the exact same next-state for every input and the same output treatment, they were never two states — merge them. This is the most common source of an over-built FSM, and it's a two-minute check that regularly halves a state count someone drew too hastily.

5

Choose Moore, Mealy, or a mix

Now that the states are settled, decide how outputs attach to them — the decision guide right below.

6

Pick the encoding, then code it

Binary, one-hot, or gray (table further down), then the two/three-always-block RTL split. Cover every state with a default/else branch, and write directed tests that hit reset, every legal edge, and — deliberately — an unreachable state if your encoding leaves any.

A frequent real mistake: modeling a wait duration as states. If what you need to remember is "how many cycles have I waited," don't draw WAIT_1, WAIT_2, … WAIT_16 as sixteen states — keep one WAIT state, add a counter register beside the FSM, and let "counter done" be one of the FSM's inputs. States are for control flow and mode; counters are for counting. Confusing the two is the single biggest cause of state count exploding for no reason.

Choosing Moore, Mealy, or a mix

Pick based on what the output actually has to do, not habit. These are the questions that settle it in practice:

Output must react within the same cycle the input arrives (a handshake, a same-cycle bypass)?Mealy
Output crosses a clock domain, drives another synchronous block as a level signal, or just needs to never glitch?Moore
You want the waveform to be readable by eye — state alone tells you the output, no need to also check the input?Moore
You're state-count or area constrained and one cycle of extra output latency is genuinely fine?Mealy
You want Mealy's state count and a glitch-free, clock-aligned output?Registered Mealy

"Mixing" almost always means one of two things in practice. First, registered Mealy: compute the output combinationally from state and input exactly like Mealy (fewest states), but land it in a flop before it leaves the block. You keep Mealy's state count and pay one cycle of latency — the same price Moore would have charged you anyway, except now it's a deliberate pipeline stage instead of a structural requirement. Second, mixed outputs within one machine: most signals are Moore (state-only, safe, easy to read) except one urgent control line that's Mealy (state+input, because it truly can't wait a cycle). Both are completely standard; neither is a compromise.

Edge cases the simple guide skips

The questions above settle most cases, but a few situations don't fit neatly into "pick one":

·

The input isn't synchronous to this clock at all. This isn't a Moore-vs-Mealy question — it's a prerequisite you solve before either one applies. A signal from another clock domain, or off-chip, needs a synchronizer (and often a debounce filter) first; only the synchronizer's clean output is a legal FSM input. Skipping this doesn't just risk a glitch, it risks metastability propagating into your state register itself. Worked example 4 below builds one end to end.

·

"Moore can't glitch" has a footnote. Moore's output can't glitch from the input, because the input never reaches it. But if state is binary- or gray-encoded, a transition that flips more than one bit can still show a brief, transient wrong decode on the output logic as the bits settle at slightly different times — a real decode glitch, just not an input-driven one. One-hot encoding sidesteps this (exactly one bit ever changes meaning per transition), which is part of why timing-sensitive Moore outputs on FPGAs often go one-hot even past the point where it costs extra flops.

·

More than one input can be asserted at once. Two requesters asking for the same resource in the same cycle is not a corner case to patch in later — it's part of the spec, and it changes how you fill the table (see step 3 of the blueprint, and worked example 5 below, which is an arbiter built entirely around this).

·

An unreachable or corrupted state needs a way home. One-hot encoding has states that are illegal by construction (two bits set, or none); binary encoding with N not a power of two leaves unused codes too. A single-event upset, an uninitialized simulation value, or a tooling bug can land the register there. A default branch that routes every unlisted code back to a safe reset state isn't defensive boilerplate — for anything safety- or mission-critical it's often an explicit sign-off requirement, and it's one line to add.

Verilog: the two/three-always-block shape

Both are written the same way in RTL: separate the registered state from the combinational logic that computes the next state and the output. Mealy's output block reads state and the input; Moore's output block reads only state.

Mealy

// state register
always @(posedge clk or posedge rst)
  if (rst) state <= S0;
  else     state <= next_state;

// next-state logic
always @(*) begin
  next_state = state;
  case (state)
    S0: next_state = in ? S1 : S0;
    S1: next_state = in ? S1 : S0;
  endcase
end

// output logic -- reads state AND in
always @(*)
  Y = (state == S1) && in;

Registered Mealy

// state register -- identical to plain Mealy
always @(posedge clk or posedge rst)
  if (rst) state <= S0;
  else     state <= next_state;

// next-state logic -- identical to plain Mealy
always @(*) begin
  next_state = state;
  case (state)
    S0: next_state = in ? S1 : S0;
    S1: next_state = in ? S1 : S0;
  endcase
end

// combinational Mealy output ...
wire Y_comb = (state == S1) && in;

// ... landed in a flop before it leaves the block
always @(posedge clk or posedge rst)
  if (rst) Y <= 1'b0;
  else     Y <= Y_comb;

Moore

// state register
always @(posedge clk or posedge rst)
  if (rst) state <= S0;
  else     state <= next_state;

// next-state logic
always @(*) begin
  next_state = state;
  case (state)
    S0: next_state = in ? S1 : S0;
    S1: next_state = in ? S2 : S0;
    S2: next_state = in ? S2 : S0;
  endcase
end

// output logic -- reads state only
always @(*)
  Y = (state == S2);

Independent of Moore vs. Mealy, you still have to pick an encoding for state. For this 2-3 state example it barely matters, but it's a near-guaranteed follow-up question:

Worked example — Moore: traffic light with pedestrian crossing

A meatier problem, run through the blueprint end to end.

1

Spec

A road crossing a pedestrian walkway. Cars normally see green. A synchronized, single-cycle pulse ped_req asks for a walk phase. Once granted, the sequence is fixed: green → yellow (fixed duration) → red-with-walk (fixed duration) → red-clearance (fixed duration, cars still stopped so stragglers finish crossing) → green again. A new ped_req arriving mid-sequence must not restart or extend anything — it's simply ignored until the cycle completes.

2

Find the states

What must be remembered is entirely "which phase of the fixed sequence am I in" — four values: GREEN, YELLOW, RED_WALK, RED_CLEAR. Notice what's not a state: how many cycles remain in the current phase. That's a duration, not a mode, so per the counter-vs-state tip above it becomes one external down-counter shared by all three timed phases, exposing a single timer_done input back to the FSM instead of thirty extra states.

3

State table — every cell filled

GREEN¬ped_reqGREENgreendon't walk0
GREENped_reqYELLOWgreendon't walk1
YELLOW¬timer_doneYELLOWyellowdon't walk0

RED_WALKtimer_doneRED_CLEARredwalk1

RED_CLEARtimer_doneGREENreddon't walk1

timer_load pulses for one cycle on entry to a timed phase, kicking off the shared down-counter; the FSM never counts anything itself.

4

Minimize

Check every pair: RED_WALK and RED_CLEAR both show car=red, but ped differs (walk vs. don't-walk) — distinct. GREEN and RED_CLEAR both show ped=don't-walk, but car differs (green vs. red) — distinct. No two rows match on every column, so four states is already minimal — there was no fat to trim here, unlike a diagram someone draws by hand under time pressure and forgets to check.

5

Why Moore

Run it against the decision guide: the car and pedestrian lights are physical signals that must never glitch, they don't need to react within the same cycle as any input, and a technician reading a waveform should be able to tell the light color from the state alone. Every criterion points the same way. There's also no candidate for a same-cycle output here — nothing downstream is waiting on a same-cycle response to ped_req — so there's no reason to reach for Mealy or a registered-Mealy signal anywhere in this machine.

6

Encoding and RTL

Four states, one clock domain, nothing crossing to another domain — plain binary (2 bits) is the ordinary choice for an ASIC target; one-hot only if this were going into an FPGA with flops to spare and decode speed mattered more than area.

localparam GREEN=2'd0, YELLOW=2'd1, RED_WALK=2'd2, RED_CLEAR=2'd3;

// state register
always @(posedge clk or posedge rst)
  if (rst) state <= GREEN;
  else     state <= next_state;

// next-state logic
always @(*) begin
  next_state = state;
  case (state)
    GREEN:     next_state = ped_req    ? YELLOW    : GREEN;
    YELLOW:    next_state = timer_done ? RED_WALK  : YELLOW;
    RED_WALK:  next_state = timer_done ? RED_CLEAR : RED_WALK;
    RED_CLEAR: next_state = timer_done ? GREEN     : RED_CLEAR;
    default:   next_state = GREEN;          // recover from an unreachable state
  endcase
end

// output logic -- reads state only (Moore)
always @(*) begin
  car_light  = RED;
  ped_light  = DONT_WALK;
  timer_load = 1'b0;
  case (state)
    GREEN:     car_light = GREEN_L;
    YELLOW:    begin car_light = YELLOW_L;               timer_load = (next_state==RED_WALK);  end
    RED_WALK:  begin car_light = RED; ped_light = WALK;   timer_load = (next_state==RED_CLEAR); end
    RED_CLEAR: begin car_light = RED;                     timer_load = (next_state==GREEN);     end
  endcase
end

Worked example — Mealy: overlapping sequence detector for 1101

This is the harder cousin of the two-state detector from the top of the page: a non-trivial pattern with a self-overlapping tail, which is exactly the case that trips people up if they try to build the table without a method.

1

Spec

On a single-bit serial input, assert Y for exactly the cycle in which the input stream's last four bits equal 1101, overlaps allowed (so ...11101... must still fire on its own 1101).

2

Find the states — track "longest matched prefix," not "bits seen"

The fact worth remembering after any prefix of the input is: what is the longest suffix of everything seen so far that is also a prefix of the target string 1101? Call that length i; the state is Si. This is the same idea behind a string-search automaton (KMP's failure function) and it's what correctly handles overlap: matching fails, you don't necessarily fall all the way back to "nothing matched" — you fall back to however much of a fresh match the tail of what you just saw already gives you for free. Work it out bit by bit from each state:

S3 has matched 110. On a 1 the full string 1101 is complete — fire Y — but the machine must land somewhere for the next bit. Drop the matched 1101 and ask: what's the longest suffix of it that's still a prefix of 1101? Suffixes are 101, 01, 1 — only 1 matches (it equals the length-1 prefix). So the fold-back lands in S1, not S0. That single fold-back edge is the entire "complicated" part of this problem.

3

State table — every cell filled

state (matched so far)input=0input=1
S0 ( — )S0 / 0S1 / 0
S1 (1)S0 / 0S2 / 0
S2 (11)S3 / 0S2 / 0
S3 (110)S0 / 0S1 / 1

Read S2's own row the same way: on another 1 the candidate is 111, whose longest prefix-matching suffix is 11 — S2 again, which matches intuition (a run of three or more 1s is still just "waiting on 01").

4

Minimize

No two rows share both a next-state pattern and an output pattern, and there's a general lower bound here too: an exact-match detector for an n-bit target needs at least n states, because it must be able to distinguish having matched every prefix length from 0 to n−1. Four is the minimum for a four-bit pattern — this table can't be shrunk further.

5

Why Mealy

There's no requirement here that forces Moore — no clock-domain crossing, nothing else on the bus reading this signal as a stable level. Mealy wins by default: fewer states would be needed if this had to grow (each new target-string bit just extends the table by one row, no fold-back state-count penalty), and the output fires the instant the fourth bit lands rather than a cycle later. If this Y were, instead, driving an interrupt to another clock domain, that would be the one thing that flips the answer to registered-Mealy — same table, same states, just land Y in a flop before it leaves the block.

6

Encoding and RTL

Four states, single domain: binary (2 bits) is the default choice, same reasoning as the traffic light.

localparam S0=2'd0, S1=2'd1, S2=2'd2, S3=2'd3;

// state register
always @(posedge clk or posedge rst)
  if (rst) state <= S0;
  else     state <= next_state;

// next-state logic
always @(*) begin
  next_state = state;
  case (state)
    S0: next_state = in ? S1 : S0;
    S1: next_state = in ? S2 : S0;
    S2: next_state = in ? S2 : S3;   // note: 0 advances S2->S3 here
    S3: next_state = in ? S1 : S0;   // the fold-back on match
    default: next_state = S0;
  endcase
end

// output logic -- reads state AND in (Mealy)
always @(*)
  Y = (state == S3) && in;

Worked example — Mixed: request/ready peripheral handshake

This one earns the "mixed" label honestly: three outputs, three different disciplines, each chosen for a specific reason rather than out of habit.

1

Spec

A small peripheral controller: IDLE, BUSY, DONE. A requester asserts req; if the peripheral is in IDLE it must assert ready in that same cycle (a same-cycle ready/valid handshake — the requester samples ready on the very edge it drove req, so a cycle of dead time is not acceptable). The peripheral then processes for a variable number of cycles, signaled by an external busy_done, then spends one cycle in DONE before returning to IDLE. When the operation completes, an external interrupt controller in a different part of the chip must also be told — but that path must never glitch.

2

Find the states

Three modes, nothing more: IDLE (waiting), BUSY (working — duration owned by an external counter, not by extra states), DONE (a one-cycle acknowledgment before returning to IDLE).

3

State table, with each output's discipline marked

stateconditionnext ready mealy busy moore done moore irq reg'd mealy
IDLE¬reqIDLE0000
IDLEreqBUSY1000
BUSY¬busy_doneBUSY0100
BUSYbusy_doneDONE0100 this cycle, 1 next
DONE(always)IDLE0011 (arrives here)
4

Minimize

All three rows differ in outputs and conditions — nothing to merge. Three is minimal.

5

Why each output got the discipline it did

ready is Mealy: the spec explicitly forbids a dead cycle, so it has to be a same-cycle function of state and req — there's no other way to meet that requirement. busy and done are Moore: nothing needs them same-cycle, and every other block in the chip reading them benefits from a clean, state-only, glitch-free signal. irq is registered Mealy: it's computed from the same same-cycle condition as the BUSY→DONE transition (so it's logically a Mealy output), but because it leaves this clock's local fanout to reach an interrupt controller elsewhere, it gets a flop before the boundary — Mealy's state count, Moore's safety, for the one signal that needs both.

6

Encoding and RTL

Three states, single domain: binary (2 bits, one code unused and defaulted back to IDLE for safety).

ready (orange) answers req in the very same cycle — cycle 2. busy (green) simply tracks the state register. done and irq (both green) land in the same cycle, 6, but for different reasons: done because the state register became DONE on that edge; irq because its flop captured the previous cycle's combinational condition. They agree here by coincidence of a one-cycle DONE phase — not because they share a mechanism.

localparam IDLE=2'd0, BUSY=2'd1, DONE=2'd2;

// state register
always @(posedge clk or posedge rst)
  if (rst) state <= IDLE;
  else     state <= next_state;

// next-state logic
always @(*) begin
  next_state = state;
  case (state)
    IDLE: next_state = req       ? BUSY : IDLE;
    BUSY: next_state = busy_done ? DONE : BUSY;
    DONE: next_state = IDLE;
    default: next_state = IDLE;
  endcase
end

// Mealy -- same-cycle handshake, reads state AND req
assign ready = (state == IDLE) && req;

// Moore -- state-only status, safe to fan out anywhere
assign busy = (state == BUSY);
assign done = (state == DONE);

// Registered Mealy -- Mealy condition, flopped before it leaves the block
wire irq_comb = (state == BUSY) && busy_done;
always @(posedge clk or posedge rst)
  if (rst) irq <= 1'b0;
  else     irq <= irq_comb;

Worked example — handling a genuinely asynchronous input

Every example so far assumed the input was already clean and synchronous. This one is about the part that happens before an FSM is even allowed to see the signal — and it's where real button, switch, and cross-domain designs actually go wrong.

1

Spec

btn_raw comes from a physical pushbutton: no relationship to this block's clock, and it chatters (bounces between 0 and 1) for several clock cycles after every physical press or release before settling. Produce press_pulse, exactly one clock cycle high per physical press, immune to both metastability and bounce. Drive a 2-state led toggle from it.

2

Find the states — except most of this problem isn't states at all

The instinct is to reach for an FSM immediately. Resist it: three of the four stages here are not control flow, they're signal conditioning, and modeling them as FSM states is the single most common over-engineering mistake in this whole area.

Stage 1 — metastability: sampling an async signal with one flop can leave that flop in an illegal in-between voltage for an unbounded time. The fix is a chain of at least two plain D flip-flops, back to back, with no logic between them — not a state, just flops whose only job is giving any metastable event time to resolve before anything downstream reads it.

Stage 2 — bounce: synchronizing doesn't remove chatter, it only cleans up the chatter that was already there. The fix is a stability check: accept a new level only once the synchronized signal has agreed with itself for some number of consecutive cycles. The wrong way to build this is a chain of states WAIT_1, WAIT_2, … WAIT_N — that's the counter-vs-state mistake from the blueprint, showing up in its most common real form. The right way is one counter plus a comparator.

Stage 3 — level vs. pulse: the debounced signal is a level — it stays high the whole time the button is held. Toggling on a level re-triggers every cycle the button stays down. The fix is an edge detector: compare the debounced value to what it was one cycle ago; a 0→1 transition is the one-cycle pulse. Forgetting this stage is the most common bug in button-driven designs, full stop.

Stage 4 — now there's an FSM: two states, OFF/ON, toggling on press_pulse. This is the only genuinely new piece of state in the whole pipeline.

3

State table — for the one real FSM in the pipeline

statepress_pulse=0press_pulse=1led
OFFOFFON0

4

Minimize

Two states, and the whole point of the machine is remembering which one led is in — can't be fewer than two.

5

Why Moore

led is a physical, persistent indicator with nothing downstream needing a same-cycle reaction to press_pulse — there's no criterion in the decision guide that points toward Mealy here. The interesting design decisions in this problem were already spent upstream, in the synchronizer and debounce stages, not in the toggle itself.

6

Encoding and RTL

One bit, two states — encoding doesn't really apply at this size.

Watch btn_sync carefully: it bounces in exactly the same pattern as btn_raw, just shifted two cycles — the synchronizer's only job was metastability, and it did that job, nothing more. btn_deb doesn't accept the high level until btn_sync has agreed with itself for two cycles running (cycles 10 and 11 both read 1). press_pulse fires for exactly one cycle, right at that acceptance — not at every bounce. led toggles the cycle after, because it's a registered Moore output.

// Stage 1: 2-FF synchronizer -- no logic between the flops
reg btn_meta, btn_sync;
always @(posedge clk or posedge rst)
  if (rst) {btn_sync, btn_meta} <= 2'b00;
  else     {btn_sync, btn_meta} <= {btn_meta, btn_raw};

// Stage 2: debounce -- a counter, not a chain of states
localparam STABLE_CYCLES = 2;
reg [1:0] stable_cnt;
reg btn_deb, btn_sync_q;
always @(posedge clk or posedge rst)
  if (rst) begin
    stable_cnt <= 0; btn_deb <= 0; btn_sync_q <= 0;
  end else begin
    btn_sync_q <= btn_sync;
    if (btn_sync == btn_sync_q)
      stable_cnt <= (stable_cnt == STABLE_CYCLES) ? stable_cnt : stable_cnt + 1'b1;
    else
      stable_cnt <= 0;
    if (stable_cnt == STABLE_CYCLES) btn_deb <= btn_sync;
  end

// Stage 3: edge detect -- level to pulse
reg btn_deb_q;
always @(posedge clk or posedge rst)
  if (rst) btn_deb_q <= 0;
  else     btn_deb_q <= btn_deb;
wire press_pulse = btn_deb & ~btn_deb_q;

// Stage 4: the actual FSM -- two states, Moore
always @(posedge clk or posedge rst)
  if (rst) led_state <= OFF;
  else     led_state <= press_pulse ? ~led_state : led_state;
wire led = led_state;

Worked example — round-robin bus arbiter

Two requesters, one resource, a fairness requirement, and a correctness requirement that forces the Mealy decision rather than just making it faster.

1

Spec

Two requesters drive req0, req1. Exactly one of gnt0, gnt1 may be high in a given cycle, and only when that requester actually asked that same cycle. If both ask in the same cycle, alternate who wins across successive contested cycles so neither starves (round-robin). A request is a single-cycle assertion — a requester may drop its request the very cycle it would have been granted, and must not be serviced a cycle late, because by then it may have stopped asking.

2

Find the states — and notice what they're not tracking

The only fact that must survive from one cycle to the next is which requester currently has priority: PRIORITY0 or PRIORITY1. That's it — two states. Notice this state is not "who is requesting" (that's an input, read fresh every cycle) and not "who was granted last" in a literal sense either — it's specifically a rotating priority pointer, and it only has two legal values, so it fits cleanly as FSM state even though it feels more like a register than a "mode."

3

State table — all four input combinations, per state

With two requesters there are four input combinations per state; small enough to enumerate directly and confirm the priority logic is actually complete:

PRIORITY11,11,0PRIORITY0

The rotation rule is deliberately narrow: priority only hands off when the currently prioritized requester is the one serviced (rows where req for the priority owner is 1). If the non-priority requester is serviced because the priority one didn't ask, the pointer holds — it still owes that requester its turn. Look closely and the next-state column depends only on the priority owner's own request line, not on the other one at all: next = req0 ? PRIORITY1 : PRIORITY0 from PRIORITY0, and the mirror from PRIORITY1. The grant output needs both request lines; the next-state logic doesn't need to. That asymmetry is easy to miss if you build next-state and output logic as one combined block instead of two separate ones.

4

Minimize

PRIORITY0 and PRIORITY1 break the tie oppositely on the 1,1 row — that's the entire reason they're different states, and it's a real difference, so two is minimal. You cannot arbitrate fairly between two requesters while remembering nothing.

5

Why Mealy — and why it's not optional here

This is the sharpest version of the Mealy argument on this whole page: it's not about latency, it's about correctness. The spec says a requester may drop req the very cycle it would be granted and must not be served a cycle late. A registered (Moore or registered-Mealy) grant computed from last cycle's request is structurally a cycle behind — it would grant a requester that may have already stopped asking, and miss one that only asked this cycle. Mealy's same-cycle response is the only way to meet the spec as written. If a later revision of this interface required requesters to hold req for two cycles minimum (common on real buses, to give the arbiter room), that would reopen the question — and registered-Mealy grant becomes attractive again, the same trade as the handshake example above, just with the requester-side contract changed to make room for it.

6

Encoding and RTL

One bit, two states — and worth noting for scale: with N requesters, the "who has priority" state is normally kept as a small rotating pointer register rather than 2N enumerated priority-states, same counter-vs-state instinct as everywhere else on this page.

Cycles 1–2: both ask every cycle, and the grant genuinely alternates — fairness doing its job. Cycle 3: state entering the cycle is PRIORITY1 (from cycle 2's rotation), but only req0 asks. PRIORITY1's own rule says the pointer only leaves PRIORITY1 once req1 is actually served, so req0 is granted without rotating priority away — req1 is still owed its turn. Cycle 4 is where that turn comes due: only req1 asks, it wins, and only now does priority rotate to PRIORITY0.

localparam P0 = 1'b0, P1 = 1'b1;

// state register
always @(posedge clk or posedge rst)
  if (rst) pstate <= P0;
  else     pstate <= next_pstate;

// next-state logic -- depends only on the priority owner's own request
always @(*) begin
  case (pstate)
    P0: next_pstate = req0 ? P1 : P0;
    P1: next_pstate = req1 ? P0 : P1;
    default: next_pstate = P0;
  endcase
end

// Mealy grant -- reads pstate AND both request lines, same cycle
always @(*) begin
  gnt0 = 1'b0;
  gnt1 = 1'b0;
  case (pstate)
    P0: if (req0)      gnt0 = 1'b1;
        else if (req1) gnt1 = 1'b1;
    P1: if (req1)      gnt1 = 1'b1;
        else if (req0) gnt0 = 1'b1;
  endcase
end

Five worked examples now span every edge case this page has raised: Moore for clean physical outputs, Mealy where same-cycle response is a correctness requirement rather than a nicety, mixed disciplines in one machine, a truly asynchronous input conditioned before any FSM sees it, and priority arbitration replacing brute enumeration.
