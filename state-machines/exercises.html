Logic Design Interview Prep/ State Machines/Exercises

State machine practice

Ten problems, typical to hard. Try each on paper before opening the answer — that's where the actual learning happens. These are deliberately different problems from the five worked examples on the summary page, so working through both gives broader coverage of what actually gets asked.

1. Convert a Mealy machine to Moore typical

A Mealy machine asserts Y on the cycle it sees the third consecutive 1 in a bit stream (overlapping allowed, so a run of four or more 1s keeps asserting Y every cycle from the third one on). Its table:

stateinput=0input=1
S0S0 / 0S1 / 0
S1S0 / 0S2 / 0
S2S0 / 0S2 / 1

Convert this to an equivalent Moore machine. How many states does it need, and why exactly that many?

Show full answer

The conversion rule: for each Mealy state, look at every incoming edge and the output written on it. If all incoming edges to a state carry the same output value, that state needs only one Moore split. If incoming edges disagree, the state must be split — one new Moore state per distinct incoming output value — because a single Moore state can only emit one output value.

Check each state: S0's incoming edges (from S0, S1, S2, all on input 0) all carry output 0 → one split, call it S0 (out 0). S1's only incoming edge (from S0 on input 1) carries output 0 → one split, S1 (out 0). S2's incoming edges are the interesting one: from S1 on input 1, output is 0 (that's only the second 1 in the run); from S2's own self-loop on input 1, output is 1 (third-or-later 1). Two different incoming output values → S2 must split into two Moore states.

Moore stateYinput=0input=1
S00S0S1
S10S0S2a
S2a (2nd one)0S0S2b
S2b (3rd+ one)1S0S2b

Four states, one more than the three-state Mealy version — exactly the "+1 state" pattern from the summary page's first example, here appearing one level deeper because the pattern being detected is one bit longer.

2. Overlapping vs. non-overlapping "1010" detector typical

Design a Mealy sequence detector for 1010, once allowing overlap and once not. Identify the single transition that differs between the two versions and explain why.

Show full answer

States track the longest matched prefix of 1010: S0 (none), S1 ("1"), S2 ("10"), S3 ("101"). Derive each row the same way as the 1101 example on the summary page — drop the matched prefix on a mismatch and ask what's the longest suffix of it that's still a prefix of the target.

stateinput=0input=1
S0S0 / 0S1 / 0
S1 (1)S2 / 0S1 / 0
S2 (10)S0 / 0S3 / 0
S3 (101)overlapping: S2 / 1
non-overlapping: S0 / 1		S1 / 0

Every row is identical between the two versions except S3 on input 0 — the one transition that fires the match. Overlapping folds back to S2 ("10"), because the last two bits of the just-matched 1010 are themselves a valid two-character prefix of a fresh match. Non-overlapping throws that away on principle and resets hard to S0, even though it's leaving real partial-match progress on the table. Both are "correct" — which one you want is a spec question, not a design question, and it's worth asking an interviewer which they mean before you start drawing.

3. Is a divide-by-3 enable generator a "counter" or a "state machine"? typical

You need enable to pulse once every three clock cycles. The blueprint says duration-counting belongs in a counter, not FSM states — so is building this as a 3-state Moore machine a violation of that rule? Design it, and explain where the actual line is.

Show full answer

It's not a violation, and the distinction is worth being precise about. The anti-pattern earlier on this page was turning a bookkeeping count — one that only ever answers a single yes/no question ("has N cycles elapsed?") — into N separate states that each individually do nothing but wait. Here, the count itself is the entire behavior: every one of the three states has its own distinct, meaningful output, there's nothing else to track, and three is small. A free-running 2-bit counter with decode logic and a 3-state FSM are, at this size, literally the same circuit wearing different notation — either is fine. The rule of thumb: if every value of the count needs its own distinct behavior and the count is small, states (or an equivalent counter) are fine; if the count exists purely to produce one done bit for some other machine, that's a counter fed into an FSM input, full stop.

stateenablenext
S00S1
S10S2
S21S0
always @(posedge clk or posedge rst)
  if (rst) state <= S0;
  else     state <= (state == S2) ? S0 : state + 1'b1;

assign enable = (state == S2);

4. Minimize a 6-state machine hard

Minimize this Moore machine. More than one pair of states is redundant, and finding all of them takes more than one pass.

stateYinput=0input=1
A0CD
B0ED
C1AA
D0CF
E1AA
F1BB
Show full answer

Use partition refinement (Moore's minimization algorithm): start by grouping states purely by output, then repeatedly re-split any group whose members land in different groups on the same input, until nothing moves.

Round 0 — group by output: G0 = {A, B, D} (output 0), G1 = {C, E, F} (output 1).

Round 1 — check G0 against the round-0 groups: A goes to C(G1) on 0 and D(G0) on 1 → signature (G1,G0). B goes to E(G1) on 0 and D(G0) on 1 → same signature (G1,G0) — A and B agree. D goes to C(G1) on 0 and F(G1) on 1 → signature (G1,G1) — different. G0 splits: {A,B} and {D}.

Round 1 — check G1 against the new groups ({A,B}=G0a, {D}=G0b, {C,E,F}=G1): C goes to A(G0a) on both inputs. E goes to A(G0a) on both inputs — same as C. F goes to B(G0a) on both inputs — also the same signature, since B is in the same group as A now. G1 stays together.

Round 2: re-check {A,B} with the stable groups {A,B}, {D}, {C,E,F}: A → C(group3) on 0, D(group2) on 1. B → E(group3) on 0, D(group2) on 1. Still identical — stable. No further splits anywhere: done.

Final partition: {A,B}, {D}, {C,E,F} — six states collapse to three:

stateYinput=0input=1
X = {A,B}0ZY
Y = {D}0ZZ
Z = {C,E,F}1XX

The catch in this one: A and B look different at a glance (they go to different-named states on input 0, C vs. E) but those targets turn out to be equivalent to each other, so A and B are equivalent too. A single pass that only compares raw next-state names would have missed this and left the machine at 5 states instead of 3 — the whole reason the algorithm iterates to a fixed point instead of stopping after one round.

5. UART receiver (8N1, 16× oversampling) hard

Design the receive-side FSM for a standard UART byte: one start bit, 8 data bits (LSB first), one stop bit, no parity, sampled by a clock running at 16× the baud rate. Reject a start-bit glitch (a short noise pulse on the line shouldn't commit the receiver to an 8-bit reception), and detect a framing error if the stop bit isn't actually high.

Show full answer

Four states, not twelve. The two most common mistakes on this problem are (a) one state per data bit, DATA0...DATA7, instead of one DATA state plus a 3-bit counter, and (b) sampling the line right at the edge of a bit period instead of at its middle, which makes the receiver sensitive to clock skew between transmitter and receiver.

States: IDLE, START, DATA, STOP (plus a one-cycle FRAME_ERR pulse state). Two counters live alongside the FSM, not inside it: an oversample tick counter (0–15, one full bit period) and a data-bit counter (0–7).

  • IDLE: rx_valid=0. On rxd==0 (already synchronized/debounced — see the async-input worked example on the summary page for why that step comes first), reset the tick counter and go to START.
  • START: count ticks; at tick 7 (the middle of the bit period), re-sample rxd. Still 0 → a real start bit: reset the tick and bit counters, go to DATA. Back to 1 → it was a glitch: return to IDLE without ever entering DATA. This is the entire false-start-bit defense.
  • DATA: at tick 7 of each bit period, sample rxd into a shift register (external to the FSM) and increment the bit counter. At tick 15, reset the tick counter and move to the next bit, or to STOP once the bit counter reaches 8.
  • STOP: at tick 7, sample rxd. High → valid frame: assert rx_valid this cycle (Moore, one cycle, exactly like the DONE state in the handshake example) and return to IDLE. Low → go to FRAME_ERR.
  • FRAME_ERR: assert frame_err for one cycle, unconditionally back to IDLE.

Keep the received byte in its own shift register, separate from the FSM's state encoding — the FSM's job is deciding when to shift and when to declare the byte valid, not holding the data itself. That control/datapath split is worth stating explicitly if asked to draw the block diagram.

localparam IDLE=0, START=1, DATA=2, STOP=3, FRAME_ERR=4;

always @(posedge clk or posedge rst)
  if (rst) state <= IDLE;
  else     state <= next_state;

always @(*) begin
  next_state = state;
  case (state)
    IDLE:      next_state = rxd_sync ? IDLE : START;
    START:     if (tick == 4'd7)
                 next_state = rxd_sync ? DATA : IDLE;      // glitch rejected
    DATA:      if (tick == 4'd15 && bit_cnt == 3'd7) next_state = STOP;
    STOP:      if (tick == 4'd7)
                 next_state = rxd_sync ? IDLE : FRAME_ERR;
    FRAME_ERR: next_state = IDLE;
    default:   next_state = IDLE;
  endcase
end

assign rx_valid  = (state == STOP) && (tick == 4'd7) && rxd_sync;
assign frame_err = (state == STOP) && (tick == 4'd7) && !rxd_sync;

6. Serial two's complement hard

Bits of a number arrive serially, LSB first. Output the two's complement of the number, serially, LSB first, with no more than one cycle of latency. A separate sop (start-of-word) input marks the first bit of each new number.

Show full answer

The two's complement algorithm, bit-serial: copy bits unchanged, LSB first, until — and including — the first 1; invert every bit after that. Two states capture it exactly:

statemeaninginput bit boutputnext state
COPYhaven't copied a 1 yet00COPY
COPY11INVERT
INVERTalready copied the first 101INVERT
INVERT10INVERT

It's Mealy (output = state and input, same cycle) — there's no reason to delay, and nothing here crosses a clock domain. The genuinely easy-to-miss part isn't the state count, it's that this FSM has no idea where one number ends and the next begins in a continuous bit stream: without the external sop signal forcing a return to COPY, state would leak across word boundaries and corrupt every number after the first. Any serial, word-at-a-time FSM needs an explicit framing signal like this — it's easy to design the "steady state" logic correctly and forget the boundary case entirely.

always @(posedge clk or posedge rst)
  if (rst)      state <= COPY;
  else if (sop) state <= COPY;        // re-arm at the start of every word
  else          state <= (state==COPY && b) ? INVERT : state;

assign y = (state == COPY) ? b : ~b;

7. Binary number divisible by 5, MSB first hard

Bits of an unsigned binary number arrive serially, most significant bit first. After each bit, assert Y if the number read so far is divisible by 5.

Show full answer

This is a direct hardware port of a classic automaton-theory construction. Reading MSB-first, each new bit b updates the value as new_value = 2×old_value + b. Since we only ever care about divisibility by 5, the state doesn't need to hold the whole value — just the remainder mod 5, which only has 5 possible values. Let state Sr mean "remainder is r so far"; on bit b, next = (2r + b) mod 5.

state (remainder)input=0input=1
S0S0S1
S1S2S3
S2S4S0
S3S1S2
S4S3S4

Moore, trivially: Y = (state == S0), true at reset (0 is divisible by 5) and true again every time the running remainder returns to 0. Five states is also provably the minimum — there are exactly five residues mod 5, and two different residues can always be driven to different outcomes by appending the right suffix, so no two states are equivalent.

8. Alternating-bit detector over the last 3 samples typical

Assert Y whenever the current bit together with the previous two form a perfectly alternating pattern — 010 or 101 — checked every cycle (a sliding window, not a one-shot match).

Show full answer

When the thing you must remember is "the last N bits, verbatim," the state is the window itself — no cleverness needed, just name each state after the two bits it's currently holding. Let Sxy mean "the two most recently seen bits were x then y" (x older). On a new bit b, the full 3-bit window is (x, y, b); classify it, then shift: next state is Syb.

state (last 2 bits)input=0input=1
S00S00 / 0 (000)S01 / 0 (001)
S01S10 / 1 (010)S11 / 0 (011)
S10S00 / 0 (100)S01 / 1 (101)
S11S10 / 0 (110)S11 / 0 (111)

This is a different flavor of FSM from the match-progress detectors elsewhere on this page (1101, 1010): there's no "fold back on mismatch" logic to derive, because every state is reachable from every other state and nothing is ever being matched against a fixed target — the state is just a literal shift register, and the output is a one-line classifier on its contents.

9. Generalize the round-robin arbiter to 4 requesters hard

The summary page's arbiter example handles 2 requesters with a 2-state machine and a specific rotation rule ("priority only hands off when the current priority owner is actually served"). Generalize to 4 requesters. Does the same rotation rule still work?

Show full answer

No — and this is the catch. With exactly 2 requesters, "rotate only when the priority owner is served" and the simpler, more standard rule "always rotate the pointer to one past whoever was just granted" happen to produce identical results, because mod-2 arithmetic only leaves one other slot to land on either way. They stop agreeing the moment there are more than two requesters.

Concrete counterexample at N=4: priority pointer = requester 0, and only requester 2 asks (0, 1, and 3 are silent). Requester 2 is granted. The 2-requester rule says "the priority owner (0) wasn't served, so the pointer stays at 0." The standard rule says "always advance past whoever was granted: pointer becomes (2+1) mod 4 = 3." These disagree, and for N>2 it's the second rule — always rotate past the granted requester — that's the actual industry-standard definition of round-robin fairness; it's simpler and still fair over time, and it's what a real arbiter should implement.

At this scale (16 input combinations per state, times 4 states), enumerating every cell by hand is the wrong tool — this is exactly the "priority chain instead of brute truth table" case from the blueprint. The standard structure is mask-based priority encoding:

// priority register: who's at the front of the rotation
always @(posedge clk or posedge rst)
  if (rst) ptr <= 2'd0;
  else if (|gnt) ptr <= grant_id + 2'd1;      // always past whoever was granted

// first try: only requesters at or after ptr (priority order), wrapping
wire [3:0] masked_req = req & ~((1 << ptr) - 1'b1);
wire [3:0] req_to_encode = |masked_req ? masked_req : req;  // wraparound if none above ptr asked

// grant_id = index of the lowest set bit in req_to_encode (priority encoder)
// gnt = one-hot decode of grant_id, qualified by (req_to_encode != 0)

The state here is still just "who's at the front of the rotation" — the same idea as the 2-state machine, just with 4 possible values instead of 2, carried in a 2-bit pointer register rather than drawn as 4 named states on a diagram.

10. Write the illegal-state recovery for a one-hot FSM typical

A 3-state FSM (A, B, C) is one-hot encoded in 3 bits, so only codes 001, 010, 100 are legal — the other five 3-bit values are illegal by construction. Write the recovery logic, and give two concrete reasons (beyond "good practice") that this matters.

Show full answer

Reason 1 — single-event upset. A cosmic ray or alpha particle can flip a bit in a flip-flop in the field. If that happens to the state register, it can land on one of the five illegal codes. Without defined recovery, the next-state logic for that case is simply unspecified — the design might latch up, output garbage indefinitely, or behave however synthesis happened to implement the "don't care."

Reason 2 — simulation and power-up. Real flip-flops don't reliably power up to a known value, and simulators often model that as X. If illegal states aren't given an explicit, defined transition, an X can propagate through the state register indefinitely in simulation, masking genuine bugs behind "it's probably just an X propagation issue" instead of a clean, deterministic trace. For anything safety-relevant (automotive, aerospace), reachability of a defined safe state from every possible register value, not only the intentionally-reachable ones, is often an explicit sign-off requirement, not a style preference.

localparam A = 3'b001, B = 3'b010, C = 3'b100;

always @(*) begin
  next_state = A;               // safe default
  case (state)
    A: next_state = cond_ab ? B : A;
    B: next_state = cond_bc ? C : B;
    C: next_state = cond_ca ? A : C;
    default: next_state = A;    // catches all 5 illegal one-hot codes
  endcase
end
