Logic Design Interview Prep/Clock Division

Clock division: ÷2, ÷3, ÷N

One chip, one fast reference clock, and a dozen different subsystems that each want a slower, cleaner-shaped clock of their own. Dividing by a power of two is almost free. Dividing by an odd number is where the real interview lives — and the single most important answer in this whole topic is a practical one: real chips almost never do this the way the "design a divide-by-N circuit" question makes it sound.

Terms, from scratch: frequency, period, duty cycle

Every clock is just a signal that goes high, then low, then high again, forever, as evenly as the hardware generating it can manage. A handful of words describe the shape of that repetition, and they get used constantly from here on.

Period (T)
How long one full repeat takes — rising edge to the next rising edge. Measured in seconds (practically: nanoseconds, picoseconds).
Frequency (f = 1/T)
How many full repeats happen per second. Measured in Hz. A 1 GHz clock repeats one billion times a second, so its period is 1 nanosecond — frequency and period are just reciprocals of each other, never two independent facts.
Duty cycle
t_high / T, usually quoted as a percentage. A "50% duty cycle" clock spends exactly half of every period high and half low — the shape most clock sources aim for by default, and the shape most of this page is about preserving (or deliberately giving up) when dividing.
Rising edge / falling edge
The instant of a low-to-high or high-to-low transition. Most digital logic (always_ff @(posedge clk)) only cares about the instant of the edge — not the voltage level in between.

Unit conversions, and how to remember them

Since f = 1/T, frequency units and time units are just reciprocals of each other — and because both the metric frequency prefixes (kilo, mega, giga, tera) and the metric time prefixes (milli, micro, nano, pico) each step by exactly 1000 per level, the two ladders line up perfectly, rung for rung. Memorize the pairing, not a pile of separate numbers.

Converting a value that isn't a clean "1"

Two steps, every time: find the round-number pair for the prefix you're given, then take the reciprocal of just the leftover numeric coefficient.

Example: what's the period of 500 MHz?
1 MHz ↔ 1 μs (the pair). 500 MHz is 500 × (1 MHz), so its period is 1/500 × 1 μs = 0.002 μs = 2 ns.

Example: what frequency has a 2.5 ns period?
1 ns ↔ 1 GHz (the pair, read backward). 2.5 ns is 2.5 × (1 ns), so the frequency is 1/2.5 × 1 GHz = 0.4 GHz = 400 MHz.

It's a precision spec, not a frequency unit itself, but it shows up in the same conversations as everything on this page.

Why divide at all

A chip typically has exactly one (or a small handful of) fast reference clocks — a crystal oscillator, a PLL output — but very few things on the chip actually want to run that fast. A status LED heartbeat wants roughly 1 Hz. A UART wants a clock tied to a specific baud rate. A slower peripheral bus might be specified to run at a clean fraction of the core clock. Clock division is how all of those slower, specific rates get produced from the one fast source everything starts from.

Divide by 2: the toggle flip-flop

Tie a T flip-flop's input permanently to 1. It toggles on every rising edge of whatever clocks it. Two toggles make one full output cycle, so the output period is exactly twice the input period — divide by 2.

module clk_div2 (
    input  logic clk_in,
    input  logic rst_n,     // active-low, synchronous
    output logic clk_out
);
    always_ff @(posedge clk_in) begin
        if (!rst_n) clk_out <= 1'b0;
        else        clk_out <= ~clk_out;   // D = T^Q with T tied to 1 -- always toggle
    end
endmodule

Divide by 4, 8, 2ⁿ: chain the toggles

Feed one toggle flip-flop's output into the clock input of the next one. Each stage independently divides whatever frequency it receives by 2, so N stages in a row divide the original clock by 2ⁿ. This is a ripple counter: only the first stage is clocked by the real clock — every later stage is clocked by the previous stage's output.

Duty cycle survives the chain, though: every individual toggle stage still produces exactly 50% duty from whatever rising edges it's given, regardless of that input's own duty cycle — so the final output after N stages is still a clean 50%, even though its edges are now skewed relative to the original clock.

module clk_div4_ripple (
    input  logic clk_in,
    input  logic rst_n,
    output logic clk_out    // clk_in / 4
);
    logic q1;    // clk_in / 2 -- this is ITSELF used as a clock below

    always_ff @(posedge clk_in) begin
        if (!rst_n) q1 <= 1'b0;
        else        q1 <= ~q1;
    end

    // INTERVIEWER Q: what's unusual about this always_ff's sensitivity list?
    //   -> it's clocked by q1, not clk_in -- a ripple stage, exactly the
    //      skew-accumulating structure described above. Most lint flows
    //      will flag "clocked by a non-primary clock net" right here.
    always_ff @(posedge q1) begin
        if (!rst_n) clk_out <= 1'b0;
        else        clk_out <= ~clk_out;
    end
endmodule

Synchronous counters vs. ripple counters

Ripple (asynchronous)

Dead simple to draw — just chain toggle flip-flops. The cost is that accumulated clock-to-Q delay: stage N's edge arrives roughly N × t_clk-to-Q after the original reference edge. Fine for a couple of stages; a real timing liability for anything deep.

Synchronous

Every flip-flop is clocked directly by the same original clk_in; combinational next-state logic computes all bits' new values at once (a plain binary up-counter). No accumulated skew — every bit changes within one clock-to-Q delay of the real reference edge, same as any other synchronous logic. More gates, no ripple.

Divide by N, even N

A free-running counter from 0 to N−1, with the output simply held high for the first half of the count and low for the second half: clk_out = (count < N/2). Since N is even, N/2 is a whole number of input periods — exactly 50% duty, period = N input clocks.

module clk_div_even #(
    parameter int N = 6          // MAGIC NUMBER: must be even for exact 50% duty
) (
    input  logic clk_in,
    input  logic rst_n,
    output logic clk_out
);
    localparam int CW = $clog2(N);
    logic [CW-1:0] count;

    always_ff @(posedge clk_in) begin
        if (!rst_n) count <= '0;
        else        count <= (count == N-1) ? '0 : count + 1'b1;
    end

    // INTERVIEWER Q: this is a synchronous counter -- is this comparator
    // at risk of the same combinational-decode glitches as a ripple
    // counter's decode logic?
    //   -> much less so: every bit of `count` is updated by the SAME
    //      always_ff off the SAME clk_in edge, so there's no inter-bit
    //      skew the way there is between ripple stages clocked by
    //      different, delayed signals. Still worth registering
    //      clk_out below if it's driving anything timing-sensitive.
    assign clk_out = (count < N/2);
endmodule

Divide by N, odd N — the hard case

For odd N, splitting N whole input periods into two exactly equal halves is impossible — N/2 isn't a whole number. Using only one clock edge (the usual rising edge), the best you can do is round: ceil(N/2) periods high and floor(N/2) low, which for N=3 means 2 periods high, 1 low — a 66.7% duty cycle, not 50%.

The key insight that fixes it: a clock edge every input period gives you resolution of one whole period. But a clock has two edges per period — using both the rising and falling edge doubles your resolution to half a period. Over N input periods there are 2N half-periods, and you need exactly N of them high for 50% duty. N is always a whole number — so splitting into "N halves high, N halves low" is always exactly achievable, odd N or not. Dual-edge logic gets you exact 50% duty for any divide ratio.

Worked through for N=3 (3 input periods = 6 half-periods; clk_in assumed 50% duty so rising/falling edges alternate every half period):

Structurally: two small mod-3 counters, one advancing on the rising edge of clk_in, one advancing on the falling edge, feeding set/reset logic (an SR latch, covered on the Flip-Flops page) that sets clk_out when the posedge counter completes its cycle, and clears it when the negedge counter completes its own, offset cycle.

module clk_div3_50pct (
    input  logic clk_in,
    input  logic rst_n,
    output logic clk_out
);
    logic [1:0] cnt_p;   // posedge-triggered mod-3 counter -- SETS clk_out
    logic [1:0] cnt_n;   // negedge-triggered mod-3 counter -- CLEARS clk_out

    // INTERVIEWER Q: why does cnt_p reset to 2, not 0?
    //   -> so the very first posedge after reset immediately wraps
    //      2->0 and sets clk_out high right away, matching the
    //      verified timing diagram above (clk_out goes high exactly
    //      on a posedge). A different reset value is possible, but
    //      must be chosen deliberately, not left to default to 0.
    always_ff @(posedge clk_in) begin
        if (!rst_n) begin
            cnt_p   <= 2'd2;
            clk_out <= 1'b0;
        end else if (cnt_p == 2'd2) begin
            cnt_p   <= 2'd0;
            clk_out <= 1'b1;             // SET
        end else begin
            cnt_p <= cnt_p + 1'b1;
        end
    end

    // INTERVIEWER Q: clk_out is written by TWO separate always_ff
    // blocks -- isn't that illegal / a lint error?
    //   -> it's exactly the SR-latch pattern from the Flip-Flops page,
    //      expressed with two edge-triggered processes instead of two
    //      gates: one block only ever SETS, the other only ever
    //      CLEARS, and posedge/negedge never happen at the same
    //      instant, so there's no real race. Most lint rules will
    //      still flag "multiple drivers" here and need an explicit
    //      waiver -- know this before a tool surprises you with it.
    always_ff @(negedge clk_in) begin
        if (!rst_n) begin
            cnt_n <= 2'd2;
        end else begin
            if (cnt_n == 2'd0) clk_out <= 1'b0;   // about to become 1 -- CLEAR
            cnt_n <= (cnt_n == 2'd2) ? 2'd0 : cnt_n + 1'b1;
        end
    end
endmodule

Worth tracing by hand against the timing diagram above: with cnt_p starting at 2, the first posedge wraps it to 0 and sets clk_out immediately (matching the diagram's "goes HIGH on a posedge" at t=0); with cnt_n also starting at 2, the second negedge (not the first) is the one where cnt_n reaches 1 and clears clk_out — exactly the negedge at t=1.5T in the diagram, not the one at t=0.5T.

Not every consumer of a divided clock actually needs 50% duty — plenty of digital logic only cares about edge timing, not the shape in between, as long as both the high and low times clear the flip-flop's minimum pulse-width spec. If 50% isn't a real requirement, the simple single-edge counter-and-compare approach (accepting a skewed duty cycle) is far less hardware. Always worth asking which one is actually needed before building the harder circuit.

What real chips actually do: a clock enable, not a new clock

Everything above answers "how do you build a divided clock" — but in a real ASIC, actually routing a counter-derived signal as the clock input to other flip-flops is rare, and for good reason: it creates a brand-new clock domain (with its own skew, its own clock tree, and a CDC boundary anywhere it talks to the original fast domain), and ripple-style dividers add glitches and accumulated delay on top of that.

The standard practical answer instead: keep every flip-flop on the same fast reference clock, and generate a one-cycle-wide clock enable pulse that fires every Nth fast cycle. Flip-flops that logically "run" at the slower rate just gate their own update with that enable: if (clk_en) q <= d;. Nothing about the clock tree changes; there's only ever one real clock domain.

module clk_en_gen #(
    parameter int N = 10          // fire one enable pulse every N clk cycles
) (
    input  logic clk,             // the ONE real clock -- never gated, never divided
    input  logic rst_n,
    output logic clk_en           // one-cycle-wide pulse
);
    localparam int CW = $clog2(N);
    logic [CW-1:0] count;

    always_ff @(posedge clk) begin
        if (!rst_n) begin
            count  <= '0;
            clk_en <= 1'b0;
        end else if (count == N-1) begin
            count  <= '0;
            clk_en <= 1'b1;        // exactly one cycle wide
        end else begin
            count  <= count + 1'b1;
            clk_en <= 1'b0;
        end
    end
endmodule

// Usage elsewhere -- still the SAME fast clk, no new clock domain at all:

//       if (clk_en) slow_reg <= next_value;   // only updates 1-in-N cycles

Gotchas

"A divided clock from a counter is just as clean as the original."
Not if it's combinationally decoded from multiple counter bits — different bits can change at slightly different times, and a combinational function of several of them can glitch briefly before settling. Build the divided output from registered toggles/latched set-reset logic, not raw combinational decode, if it's ever going to be used as an actual clock.

"Odd dividers are just like even ones, a little less tidy."
They need a fundamentally different technique — single-edge logic cannot hit exact 50% duty for odd N at all; it takes dual-edge (half-period resolution) logic to get there.

"Ripple counters are fine for any divide ratio."
Delay accumulates linearly with stage count — each stage adds roughly one clock-to-Q delay relative to the original reference edge. Fine for 2–3 stages, a real liability deeper than that; prefer a synchronous counter.

"The divided clock's phase is well-defined from the first cycle after reset."
Not necessarily for odd dividers — the posedge- and negedge-triggered counters need to reach their steady, offset relationship first; the very first output period after reset can be irregular until they do. Worth stating explicitly rather than assuming.

"If I need something N times slower, I should build a divided clock."
Usually not — see "What real chips actually do" above. A clock enable on the existing fast clock avoids creating a second clock domain (and the CDC boundary that comes with it) entirely.

Interview Q&A

Interviewer: Design a divide-by-4 clock.

You: Two toggle flip-flops in series — each one divides by 2, so two stages give divide-by-4. Quick follow-up I'd flag myself: that's a ripple counter, so the second stage's edges are delayed slightly relative to the original clock by accumulated clock-to-Q delay. If that matters, a synchronous 2-bit counter avoids it.

Interviewer: Now divide by 3, with 50% duty cycle.

You: That needs both clock edges. With only the rising edge, 3 periods can only split 2-and-1, which is 66.7% duty, not 50%. Using the falling edge too doubles the resolution to half-periods — 3 periods is 6 half-periods, and setting the output high on a rising edge, low on a falling edge, each driven by its own small counter, splits it exactly 3-and-3.

Interviewer: Would you actually route that as a clock to other flip-flops on a real chip?

You: Generally no — that creates a second clock domain with its own skew and a CDC boundary wherever it talks back to the fast domain, and if it's built from combinational decode it risks glitching. The usual real answer is to keep everything on the original fast clock and generate a one-cycle clock-enable pulse every 3rd cycle instead.

Cheat sheet

  • Period T, frequency f=1/T, duty cycle=t_high/T. A 50% duty clock is high for exactly half of every period.
  • ÷2: one toggle flip-flop. Always exactly 50% duty, regardless of input duty cycle.
  • ÷2ⁿ: chain N toggle flip-flops (ripple) — duty cycle stays 50%, but edges accumulate delay stage by stage. A synchronous counter avoids the accumulated delay.
  • ÷N, even N: free-running counter, output high while count < N/2 — exact 50% duty.
  • ÷N, odd N: single-edge logic cannot hit 50% duty (best case ceil(N/2)/N). Dual-edge logic (posedge sets, negedge clears, two offset mod-N counters) achieves exact 50% for any N.
  • In practice: prefer a clock-enable pulse on the existing fast clock over an actual new divided clock domain — avoids CDC boundaries, glitch risk, and ripple skew entirely.
  • Combinational decode of counter bits can glitch — build divided outputs from registered toggle/set-reset logic if they'll ever be used as a real clock.
  • Odd dividers can have an irregular first period right after reset, until their offset counters settle into steady state.
