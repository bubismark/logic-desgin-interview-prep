Sliding window: moving average, max, and min

Same shape of question every time: a stream of samples, one per clock, and a statistic over the last N of them, every cycle. It looks like an algorithms warm-up. In hardware, every "obvious" answer runs straight into a real constraint — one operation per cycle, fixed per-cycle work, bit-width growth, reset behavior — and the interviewer is really testing whether you can reason about those trade-offs, not whether you know the trick.

Setup

One M-bit sample x[t] arrives every clock cycle. The window at time t is the last N samples: {x[t-N+1], …, x[t]}. Every cycle, output a statistic over the current window — the sum/average for Part 1, the max (or min) for Part 2. Min is max with every comparison flipped, so it gets one line at the end instead of its own section.

Throughout, one running numeric example for the moving-average half: N=4, stream 3, 1, 4, 1, 5, 9, 2, 6 (the digits of π, easy to recompute by hand). For the sliding-max half, a few different short streams, each chosen to demonstrate one specific behavior.

Primer: the building blocks, from scratch

Every diagram on this page is built from a small handful of pieces. Nail these down first and nothing later will require a leap of faith.

A register (a.k.a. a flop)

A register is a box that remembers exactly one value. It has a data input, a data output, and a clock input. The instant the clock "ticks," whatever value was sitting on the input gets copied to the output — and then the output holds that exact value, rock steady, no matter what the input does next, until the next tick.

"One sample per clock"

The clock is a steady heartbeat — tick, tick, tick, evenly spaced. "One sample per clock" means exactly one new data value is guaranteed to show up in sync with every tick, like a conveyor belt dropping exactly one box per beat. Every trace table on this page has a t column for precisely this reason: t just counts heartbeats.

The boxes labeled "+", "−", or "max"

Every diagram draws arithmetic as a labeled box with lines going in and a line coming out. These have no memory inside — the instant the inputs change, the output changes too, with no clock involved. A "+" box adds its two inputs; a "max" box compares them and passes the larger one through. They're themselves built from simpler logic gates underneath, but that's a different, lower-level question than this page answers — here they're treated as clean, ready-made building blocks.

An index (or a pointer)

As each sample arrives, give it a serial number — the first is index 0, the next is index 1, and so on. The index is not part of the data; it's bookkeeping carried alongside the data purely to answer "how old is this?" A pointer is the same idea used as a memory address instead of just a label.

"Valid"

Right after reset, every register is full of 0s or leftover garbage, and nothing about the wiring can tell the difference between a real sample that happens to be 0 and a register that's simply never been loaded. valid is one extra wire whose entire job is to say, out loud, every single cycle: "yes, trust the data sitting next to me right now" or "no, ignore it." See "Reset and warm-up" below for exactly where this earns its keep.

"Critical path depth," and why it's tracked separately from "how many units"

Picture a long row of dominoes between two checkpoints that are only inspected once per clock tick. Knock over the first domino, and it takes real time for the whole row to finish toppling before the far checkpoint sees a stable, correct value. Depth is how many dominoes (adders, comparators, logic gates) are chained back-to-back in that row. The deeper the row, the longer you must wait before the next tick is allowed — a deeper chain forces a slower clock. That's why, all through this page, two different numbers get reported for every design: how many units it uses (cost/area) and how many of them sit in a row between one register and the next (depth, which caps speed). They are not the same number, and mixing them up is one of the most common mistakes covered later in the misconceptions section.

Part 1.2 — Running sum

The key realization: you don't need to re-add everything, you need to update the sum you already have. sum[t] = sum[t-1] + x[t] − x[t-N]. One add, one subtract, done.

This does not save storage. You still need to know x[t-N] — the exact value about to fall out of the window — and the sum alone can't tell you what that was. You still keep all N samples around (shift register or RAM, see next section); what changed is that you no longer need to re-read and re-add all of them every cycle.

The real downside: the accumulator carries history forward. The naive adder tree recomputes from the stored samples every cycle, so a corrupted sample only pollutes the output for as long as it's physically in the window — it's self-healing. A running sum has no such correction: a single bad update (wrong width causing silent overflow, a glitched bit) is baked into every future value forever, since nothing ever re-derives the sum from scratch again. With correct integer arithmetic and correct widths, the running sum is exact — the risk is entirely in getting the width wrong once.

Part 1.3 — Storage choice: flops vs. a circular buffer in RAM

The shift register physically moves every sample one slot to the right, every cycle — N×M flops all toggling, all the time. The alternative: leave the data still, and move a pointer. Read the oldest sample at the pointer, write the new sample into that same slot, then increment (and wrap) the pointer. One read and one write per cycle, at the same address — exactly what a simple-dual-port RAM gives you for free.

Small N (≈8–32)

Flops / shift register win outright. Even the naive adder tree is fine — RAM's fixed overhead (address decode, sense amps, control) isn't worth paying yet.

Large N (hundreds–thousands)

On-chip RAM circular buffer + running sum. An SRAM bit cell (≈6 transistors, shared decoders/sense-amps) is far denser than a flop (≈15–20 transistors plus per-bit clock load) at this scale.

Huge N (e.g. 250k-deep, many channels)

External memory + running sum — only viable once the per-cycle bandwidth budget allows a controller/PHY/protocol round trip at all.

There's no universally "right" answer here — it depends on N, the sample rate, and how many of these windows you're instantiating. Say that explicitly; naming the crossover is the point.

Part 1.4 — Bit widths

Two numbers of width m and n: the sum needs max(m,n) + 1 bits (one guard bit for the possible carry-out). Sum N numbers of width M, and the rule is not "N+M" — it's M + ceil(log₂N).

ClaimWhy
Four 2-bit numbers (max 3 each) → max sum 12needs 4 bits (2⁴=16>12) = M+ceil(log₂4) = 2+2 = 4 ✓
Formula is a safe upper bound, not always the tighteste.g. ten 2-bit numbers: true max = 30, needs 5 bits; the formula gives 2+ceil(log₂10)=2+4=6 — one extra guard bit when N isn't a power of two. The formula is always sufficient, and exactly tight whenever N is a power of two.

Two's complement doesn't change the growth rule — N bits still hold 2N values, just straddling zero instead of starting at it. Use sign extension instead of zero extension when widening, and the same M+ceil(log₂N) rule applies unchanged.

Contrast with multiplication: a product of an m-bit and an n-bit number needs m+n bits — genuinely different growth from a sum, and a very common mix-up under interview pressure.

When N is a power of two, "divide by N" for the average is just dropping the bottom log₂N bits — free in hardware, no divider needed.

Part 1.5 — Reset and warm-up

Shift-register version

Reset every register to 0 (a plain synchronous reset is typical for a datapath like this). The problem: right after reset the window is full of zeros, so the first N−1 outputs are not real averages of N real samples. Fix: a small counter that counts real samples since reset, plus a valid output that only asserts once the counter reaches N.

RAM version

Do not clear the RAM — that would cost N cycles you don't have. Reset only the write pointer, the running-sum register, and the fill counter. Stale RAM contents are never trusted, because valid stays low until N real samples have overwritten every slot. Subtlety: during warm-up, the value read back as "oldest" is garbage — gate the subtract to 0 until the buffer is actually full.

Optional refinement: divide by the actual sample count instead of N during warm-up (so you get a true running average from sample 1 instead of waiting for valid). This needs a real divider, since the count isn't generally a power of two during warm-up — a legitimate extra cost to flag rather than hand-wave past.

Part 1.6 — Alternatives that avoid storing N samples

Exponential moving average (EMA)

avg += (x − avg) >> k. No sample storage at all — one add/subtract and a shift. Trade-off: it's not a true N-sample window; it's an infinite-impulse-response filter with exponentially decaying memory of every past sample, and a different frequency response than a hard boxcar window.

CIC (integrator-comb) filter

The hardware-standard, production-grade version of the running-sum trick, used for decimation in DSP front ends: an integrator (running sum) followed by a comb (the delayed-subtract). Cascading multiple stages improves the stopband at the cost of more pipeline depth.

What the interviewer will ask next — Part 1

"N isn't a power of two — what now?"
The subtract/add logic is unchanged; only the divide changes. Either a real divider, or multiply by a precomputed reciprocal and shift (fine if N is fixed at build time).
"What if samples are signed?"
No change at all — two's-complement add/subtract is the identical circuit for signed and unsigned; only the bit-growth interpretation (sign vs. zero extension) differs.
"Can you get the output the same cycle the input arrives, with zero extra latency?"
Yes with a running sum (the adder/subtractor output can be tapped combinationally before the register, if timing allows) — much harder with the naive version if the adder tree itself doesn't fit in the cycle.
"What if N needs to be programmable at runtime?"
RAM version handles it naturally — the wrap modulus is just a comparator against a register instead of a constant. The shift-register version needs a mux tree picking which tap to sum, which is awkward and still needs an adder tree sized for the worst-case N.
"What if the output must fit in fewer bits than M+ceil(log₂N)?"
Saturate or truncate — state which one, and that it's a deliberate lossy choice, not an oversight.

Part 2.1 — Rejected: sort every cycle

A full sorting network costs roughly N×log₂N² compare-swap units and produces a total ordering of the whole window. You only ever want the single largest value — paying to compute a full sort every cycle is solving a much harder problem than the one that was asked.

Part 2.2 — Naive: shift register + comparator tree

Structurally identical to the moving-average adder tree — swap every + for a max comparator.

Part 2.3 — Why a "running max" doesn't work

Adding a new sample is trivial: running_max = max(running_max, x_new). The problem is eviction. Sum has subtraction as its exact inverse; max has no inverse at all. Concrete example: window is {5, 3, 2}, running max register holds 5. Now 5 slides out of the window, and a new sample 1 slides in: new window is {3, 2, 1}, true max is 3. But the register only ever held the single number 5 — there is no way to recover 3 from it. The information about what the second-largest value was has already been thrown away.

"Just keep a second-max register too" survives exactly one eviction — the moment that value also needs to leave, you're stuck again, and need a third, a fourth… which is just keeping the whole window sorted, one register at a time.

Part 2.4 — The key insight: domination

If a newer sample is ≥ an older one still in the window, the older one can never be the max again, for as long as both remain candidates — the newer, bigger value will always still be around whenever the older one would have been the answer. The older value is now useless. Discard it immediately, rather than waiting for it to expire naturally.

Part 2.5 — The monotonic deque

Keep only the survivors — candidates that haven't been dominated yet — in a double-ended queue, strictly decreasing from front (oldest surviving, also the current max) to back (newest).

Why does it need two ends? A plain FIFO isn't enough

A FIFO (first-in-first-out queue) only ever removes things from the front, strictly in the order they arrived — nothing can jump the line. But we need to throw things away for two completely different reasons, at two different ends: a value gets removed from the back the instant something bigger and newer shows up (domination — see above), and, separately, a value gets removed from the front simply because it's aged out of the window (expiry), regardless of its size. Those are independent events that can happen in either order, any number of times, which is exactly what "double-ended" buys you that a single-ended FIFO can't.

In plain English, before the mechanical steps: every time a new sample shows up, first throw out everyone at the back who's just been completely outclassed by it (they can never win again); then let the new sample join the back of the line; then, separately, check whether the person standing at the front is simply too old to still count — if so, retire them. Whoever is left standing at the front, after all that, is the biggest value currently in the window, guaranteed.

1

On a new sample x[t]

Pop from the back every entry whose value ≤ x[t] — they're all dominated.

2

Push

Push (x[t], t) onto the back.

3

Expire

If the front entry's index is ≤ t−N (outside the window), pop it from the front.

4

Output

The front entry's value is always the current window max.

Each entry stores (value, index) — the index is what makes expiry checkable. Both ends of the structure are genuinely used (pop-heavy at the back, pop-light at the front), so a plain FIFO isn't enough on its own. For sliding minimum: flip step 1 to pop while back ≥ x[t], and keep the deque increasing instead of decreasing — everything else is identical.

Part 2.7 — Hardware solutions to "one sample can pop many entries"

In software this algorithm is amortized O(1): across the whole stream, each element is pushed once and popped at most once, so total work is O(length of stream). That analysis says nothing about any single cycle — and hardware gets exactly one clock edge per sample, with no way to "catch up later" the way an amortized bound assumes. Trace C above is the proof: one sample, four pops, one cycle budget.

(a) Sequential pops + backpressure

Pop one entry per cycle; stall the input with a valid/ready handshake while a burst of pops drains. Correct, cheap (one comparator, reused). Only works if the average sample rate leaves idle cycles for the stalls to hide in.

(b) Bounded K-wide pops

Compare the new sample against the last K entries in parallel; drop all K-or-fewer losers in one cycle. Cheap for small K, and shrinks the common case, but a burst needing more than K pops still needs another round (or a stall) — it doesn't remove the worst case unless K=N.

(c) Fully parallel hardware deque

Keep the (already-sorted, decreasing) deque in an N-register array. Compare the new sample against all N entries at once. Because the array is sorted, the dominated entries are always a contiguous tail — a priority encoder finds the cut point in one cycle, and a shift/insert network compacts the array and drops the new value in. Guaranteed 1 sample/cycle, at the cost of N comparators plus a non-trivial shift network — materially more hardware than a plain FIFO.

What's a priority encoder, exactly? A box that takes in a row of yes/no bits and outputs the position of the first "yes," reading in whatever direction you define as first. Example: feed in 0,0,1,1 (reading left to right) and it outputs 2 — the position of the first 1. Here, each bit answers "is this deque slot dominated by the new sample?", and the encoder finds, in one step, exactly where the surviving entries end and the dominated tail begins — no matter how many entries that tail has.

(d) Block-based (van Herk / Gil–Werman)

Deterministic, data-independent work: ~3 comparisons per sample, always — see the worked trace below.

Van Herk / Gil–Werman, worked (N=4, two blocks of 4)

Split the stream into blocks of size N. Within each block, keep a prefix max (running max left-to-right) and a suffix max (running max right-to-left). The window ending at position i spans [i-N+1, i]; its max is max(suffix_max[i-N+1], prefix_max[i]) — true whether that range sits inside one block or straddles two, because each side only ever needs max-to-the-end-of-its-own-block / max-from-the-start-of-its-own-block.

What the interviewer will ask next — Part 2

"What changes for sliding minimum?"
Flip every comparison (pop back while ≥ instead of ≤), keep an increasing deque instead of decreasing. Identical structure otherwise.
"What if you need both max and min at once?"
Two independent deques, one increasing and one decreasing, run off the same incoming stream — they don't share state, just the input.
"What's the actual worst-case latency of the parallel hardware deque (option c)?"
One cycle for the compare + priority-encode + shift, if that whole chain fits your clock period; for large N the shift/insert network's own depth becomes the thing you have to budget for, same story as any wide operation.
"Why not just use option (d) always, since it's deterministic?"
Latency: it needs roughly 2N samples of buffering before the first valid output, versus the deque's much shorter fill time. Deterministic worst-case work and low latency are different axes — pick based on which one the spec actually constrains.

Common misconceptions, corrected

"The sum of N M-bit numbers needs N+M bits."
Correct: M + ceil(log₂N). Four 2-bit numbers (max 3 each) sum to at most 12 — 4 bits, not 6.

"Two's complement makes bit growth one-to-one."
It doesn't. Same capacity (2N values), just shifted to straddle zero. Growth rule is unchanged; use sign extension instead of zero extension.

"The running sum saves storage."
It doesn't — it saves arithmetic. You still need every sample in the window stored somewhere, to know what's about to leave.

"RAM is always cheaper than flops."
Only above a crossover N. RAM carries fixed overhead (decode, sense amps, control); for small N, flops plus even a naive adder tree win outright.

"A comparator tree needs log N comparators."
It needs N−1 comparators; log₂N is the depth, not the count — two different numbers.

"Keeping a second max solves sliding max."
Only survives one eviction. The moment the second-largest value also needs to leave, you're back to square one.

"The deque only needs two entries."
Worst case, all N. Trace B above (a strictly decreasing stream) proves nothing ever gets dominated, so the deque fills completely.

"Pointers solve the multiple-evictions problem."
Pointers locate entries; they don't create the hardware to retire several per cycle. You still need either the backpressure, the bounded-K compare, the fully parallel array, or the block-based method above — a pointer alone doesn't make four simultaneous pops free.

Mock interview script

Interviewer: Design hardware that outputs the moving average of the last N samples, one M-bit sample per clock.

You: Simplest correct answer: an N-deep shift register holding the window, and an adder tree summing all N values every cycle, then a shift if N is a power of two.

Interviewer: What does that cost as N grows?

You: N−1 adders, log₂N levels deep. Both area and critical path grow with N — for large N the adder tree itself can become what limits your clock.

Interviewer: Can you avoid re-summing everything every cycle?

You: Yes — keep a running sum and update it: add the new sample, subtract the one leaving. One add, one subtract, constant work regardless of N.

Interviewer: Does that save you the shift register too?

You: No — I still need to know exactly which value is leaving, so I still store all N samples somewhere. What I saved was the arithmetic, not the storage.

Interviewer: How would you store them more efficiently for large N?

You: A circular buffer in RAM instead of flops — one read (the oldest, before overwrite) and one write (the new sample) at the same pointer address each cycle, then increment and wrap the pointer. RAM is denser per bit than flops above some crossover N, at the cost of fixed per-access overhead that isn't worth it for small N.

Interviewer: What width does the sum need?

You: M + ceil(log₂N) bits, not N+M — each doubling of N costs one more bit, not each additional sample.

Interviewer: Now do the same thing, but output the max of the last N samples instead of the average.

You: The naive version is the same shape — shift register plus a comparator tree, N−1 comparators, log₂N deep. But I can't do the running-sum trick here: max has no inverse, so a single running-max register can't tell you the new max once the old max leaves the window.

Interviewer: So what's the right structure?

You: A monotonic deque: keep only values that haven't been dominated by a newer, larger value, strictly decreasing from front to back. New sample pops everything smaller off the back, then gets pushed; expired entries pop off the front; the front is always the current max.

Interviewer: What's the worst-case size of that deque?

You: N — a strictly decreasing input stream never dominates anything, so nothing ever gets popped from the back, and the deque fills completely.

Interviewer: One sample arrives and needs to pop N−1 entries off the back. You have one clock cycle. Now what?

You: That's the real hardware problem — the software amortized-O(1) argument doesn't bound any single cycle. Options: stall the input while popping sequentially if the sample rate allows idle gaps; compare against a bounded number of recent entries in parallel to cut the common case; keep the whole deque in a register array and compare against all N in parallel with a priority encoder, guaranteeing one sample per cycle at the cost of N comparators and a shift network; or restructure the algorithm entirely with a block-based method like van Herk/Gil–Werman, which bounds the work at about three comparisons per sample regardless of the data, at the cost of roughly 2N of buffering latency. Which one's right depends on the throughput guarantee and the latency budget the spec actually gives me.
