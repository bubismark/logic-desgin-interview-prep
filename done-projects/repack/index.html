Write repack: merging narrow bus writes into wide aligned beats

A block sitting between an upstream write source and a downstream engine that only wants to deal in wide, aligned writes. Upstream is allowed to send narrow bursts (a bus-width field lets it write as little as 1 byte at a time); downstream needs full-width beats. This page walks the whole design: the accumulate-and-merge datapath, the precompute-once trick that keeps a multiply off the hot path, a real off-by-one bit-width bug, the FSM, and the handshake discipline that holds it all together — with a diagram for every piece.

The problem

The upstream side of this block speaks an AXI-style write channel: an address phase (base address, burst length, and a size field encoding how many bytes wide each beat is — 1, 2, 4, 8, 16 or 32 bytes, always a power of two) followed by a data phase (one write beat per cycle, each with its own byte-strobe mask marking which bytes are actually valid). Critically, upstream is allowed to write narrower than the downstream engine wants to deal with. The downstream engine — a read-modify-write (RMW) stage that merges writes against existing memory contents — is built around one fixed, wide, aligned beat size (32 bytes, in the concrete numbers used throughout this page). Handing it four separate 8-byte writes where one 32-byte write would do means four times the downstream transactions, four times the control-channel overhead, for data that's going to the exact same aligned block anyway.

So this block's whole job is: watch narrow writes go by, and turn them into the fewest possible wide, aligned writes, without ever touching the address, without reordering anything, and without adding an expensive operation onto the path that runs every single cycle.

Block overview

Three states drive the engine: idle (waiting for a new transaction), accumulate (merging narrow beats into wide ones), and pass-through (the write is already the right width, just forward it). Everything below unpacks one piece of this at a time.

The easy case: pass-through

If the incoming write is already 32 bytes wide, there's nothing to repack — every input beat is an output beat. The engine recognizes this the moment the address phase arrives and routes the whole transaction down a bypass path: no accumulator, no byte masking, no slot tracking, just a straight copy from the input data FIFO to the output data FIFO, one beat in, one beat out. This matters as a design choice on its own: a fast path for the common/simple case, so that traffic which needs no work doesn't pay for the machinery built for traffic that does.

The core idea: accumulate and merge

For a narrow write, the fix is a single wide register — the accumulator — sized exactly to the downstream beat width (32 bytes of data, plus a 32-bit byte-strobe). Each arriving narrow beat already lands at the correct byte lanes within its 32-byte window (upstream places the data where it belongs, based on the address), so merging it in is just a bitwise OR. Once the accumulator holds everything that belongs in this output beat, push it downstream and clear the register for the next one.

Byte offsets and slots

Call each 32-byte-aligned window downstream a slot. Every input beat has a cumulative byte offset from the start of the transaction (offset[k] = starting alignment + k × bytes_per_beat), and its slot is just that offset divided by 32 — which, because 32 is a power of two, is simply offset >> 5, the top bits of the offset. The moment the next beat's slot differs from the current one, the current slot is done and gets flushed.

Design choice: precompute once, not every cycle

Here's the trap: computing a slot naively is (k × bytes_per_beat) >> 5 — a multiply, fresh, on every single beat. That's exactly the kind of operation earlier pages on this site had to pipeline around when it had to run every cycle on a hot path. Here there's a cleaner fix available: bytes_per_beat and the starting alignment are both fixed for the whole transaction (every beat in one burst is the same size). So instead of multiplying per beat, compute the whole table of slot values — one entry per possible beat index, up to 4 entries for this engine — once, at the moment the address phase is latched, using nothing but repeated addition (offset[k] = offset[k-1] + bytes_per_beat, one cheap add, not a multiply). Store it in a tiny register array. From then on, the per-beat hot path is just slot = table[beat_index] — a lookup, not an arithmetic operation.

Notice what isn't happening at any of these four cycles: no multiply, no shift, not even an add — just two table lookups (slot_tbl[beat_cnt], slot_tbl[beat_cnt+1]) and an equality check. All the real arithmetic happened once, back at AW dispatch, building the table this loop just reads.

Byte-lane masks

Each beat's mask is a 32-bit window of consecutive 1s, starting at lane_start[k] = offset[k] mod 32 and running for bytes_per_beat bits. Generating it is a simple per-bit range check: mask[k][b] = (b ≥ lane_start) && (b < lane_end), for every byte lane b — a one-hot-style window decoder, computed once per beat (from the precomputed table above, not recomputed from scratch).

A real bug: when "just one more bit" matters

This block actually shipped with (and later fixed) exactly the kind of bit-width bug the earlier addition rules on this site warn about. lane_start only ever needs to hold values 0–31, so it was declared as 5 bits. lane_end = lane_start + bytes_per_beat was declared the same width. That's fine almost always — except a 16-byte beat starting at lane 16 gives lane_end = 16 + 16 = 32, which does not fit in 5 bits.

Design choice: why one accumulator is enough

A more general design might need one accumulator per slot, or some scoreboard keyed by slot number, in case beats for different output slots show up interleaved. This block gets away with exactly one accumulator register pair, because of a guarantee the upstream burst type provides: beats arrive in strictly increasing address order within a transaction. Slot numbers can only stay the same or go up as beats are consumed — never backward, never skip-and-return. So by the time a beat for a new slot shows up, the previous slot has already been completed and flushed; there's never a need to hold two partially-filled slots at once.

Handshake discipline: gate ready, never retract valid

An AXI-style handshake has one inviolable rule: once a producer asserts valid, it must hold that value (and the data behind it) steady until the consumer asserts ready — a producer is never allowed to take valid back early just because something downstream got busy. This block's output side obeys that by applying all of its own backpressure upstream, at the ready signals it hands back to the write source, rather than ever touching its own output valid based on downstream state.

cyc 1cyc 2cyc 3cyc 4
wrong: retract validvalid=1valid=0 (!) downstream was busyvalid=1 (different data?)—
right: hold valid, gate upstreamvalid=1, stalls upstream via ready=0valid=1 (same data, held)valid=1, ready arrives, advancesnext beat

Instead of a downstream stall ever reaching back and un-asserting this block's own output valid, the stall shows up earlier: the output FIFO stops accepting new pushes (it's full), which is exactly what makes this block de-assert the ready signal it gives its own upstream. The upstream write source just sees itself stalled, the same as it would against any full FIFO — it never needs to know or care that there's a repack engine in between.

Squeezing out the idle cycle: back-to-back dispatch

The straightforward version of this FSM finishes a transaction's last beat, goes back to IDLE, and only then looks at whether another transaction is already waiting. That's a guaranteed one-cycle bubble between every pair of back-to-back transactions. The actual design checks, in the very same cycle as the last beat, whether the input address FIFO already has the next transaction waiting and the output address FIFO has room — and if so, dispatches it immediately, landing straight back in ACCUM or PASS instead of idling through IDLE first.

One extra comparison in the FSM's combinational logic (is the next transaction already sitting there, and is there room to dispatch it) buys back a cycle on every single transaction boundary — worth it whenever back-to-back transactions are common in real traffic, which for a write path usually they are.

Design tradeoffs, summarized

Merge vs. zero-pad every beat

Accumulating and merging costs an accumulator register and slot-tracking logic, but turns N narrow beats into far fewer wide ones. The alternative — zero-pad every narrow beat up to 32 bytes and send it straight through — is simpler hardware but burns downstream transaction bandwidth proportional to how narrow the traffic actually is.

One accumulator vs. a scoreboard

Relying on the upstream guarantee of strictly increasing beat order collapses what could be a multi-slot scoreboard down to one register pair. The saving only holds as long as that ordering guarantee genuinely holds upstream — it's a hardware simplification purchased with a protocol assumption, not a free lunch.

Precompute vs. pipeline

A per-beat multiply could instead have been pipelined (the companion page's whole subject). Here it's cheaper to notice the operation is constant across a whole burst and do it once, off the hot path, at dispatch time — a different fix for the same underlying problem, worth recognizing as its own option.

Decoupled AW/W vs. one combined channel

Separate address and data FIFOs let the address phase reach downstream before any data has arrived, lowering address-visibility latency, at the cost of holding "current transaction" context (bytes-per-beat, slot table) in registers for however long the data phase takes to trickle in.

A generic implementation

// Generic re-implementation of the accumulate-and-merge engine worked
// through above -- fresh names, debug/BP-test infrastructure and the
// downstream address channel omitted so the repack logic stays in focus.
// Illustrative / simplified for teaching, not meant to drop into a real
// flow as-is.

module write_repack #(
    parameter int OUT_BYTES = 32,   // downstream beat width -- MAGIC NUMBER: must match the RMW engine's native width
    parameter int MAX_BEATS = 4     // longest burst this engine supports
) (
    input  logic                    clk,
    input  logic                    rst_n,        // active-low, synchronous

    // upstream address phase (one-shot per transaction)
    input  logic                    up_aw_valid,
    output logic                    up_aw_ready,
    input  logic [5:0]              up_aw_bytes_per_beat, // decoded from a size field: 1,2,4,8,16,32
    input  logic [1:0]              up_aw_len,            // burst length - 1 (0..3 -> 1..4 beats)

    // upstream data phase (one beat per cycle)
    input  logic                    up_w_valid,
    output logic                    up_w_ready,
    input  logic [OUT_BYTES*8-1:0]  up_w_data,
    input  logic [OUT_BYTES-1:0]    up_w_strb,
    input  logic                    up_w_last,

    // downstream data phase
    output logic                    dn_w_valid,
    input  logic                    dn_w_ready,
    output logic [OUT_BYTES*8-1:0]  dn_w_data,
    output logic [OUT_BYTES-1:0]    dn_w_strb,
    output logic                    dn_w_last
);

    localparam int LANE_W = $clog2(OUT_BYTES);             // 5, for OUT_BYTES=32
    localparam int SLOT_W = $clog2(MAX_BEATS);             // 2, for MAX_BEATS=4
    localparam int CNT_W  = $clog2(MAX_BEATS + 1);
    localparam int OFF_W  = $clog2(MAX_BEATS * OUT_BYTES); // 7, for 4*32=128

    typedef enum logic [1:0] {ST_IDLE, ST_ACCUM, ST_PASS} state_e;
    state_e state, state_n;

    // ---- per-transaction precomputed tables -- built ONCE per AW, not per beat ----
    logic [SLOT_W-1:0]    slot_tbl [MAX_BEATS];
    logic [OUT_BYTES-1:0] mask_tbl [MAX_BEATS];
    logic [CNT_W-1:0]     num_beats_r;
    logic [SLOT_W-1:0]    last_slot_r;

    // ---- per-beat bookkeeping ----
    logic [CNT_W-1:0]  beat_cnt;
    logic [SLOT_W-1:0] out_beat_idx;

    // ---- the one shared accumulator -- see "Why one accumulator" above ----
    logic [OUT_BYTES*8-1:0] accum_data;
    logic [OUT_BYTES-1:0]   accum_strb;

    logic                   is_last_in_beat, slot_boundary, beat_completes;
    logic [OUT_BYTES-1:0]   cur_mask;
    logic [OUT_BYTES*8-1:0] masked_data;
    logic [OUT_BYTES-1:0]   masked_strb;

    assign is_last_in_beat = (beat_cnt + 1'b1 == num_beats_r);
    assign slot_boundary   = !is_last_in_beat
                           && (slot_tbl[beat_cnt[SLOT_W-1:0]] != slot_tbl[beat_cnt[SLOT_W-1:0] + 1'b1]);
    assign beat_completes  = is_last_in_beat || slot_boundary;
    assign cur_mask        = mask_tbl[beat_cnt[SLOT_W-1:0]];

    // INTERVIEWER Q: why mask the data at all -- doesn't upstream already
    // place bytes in the right lanes?
    //   -> masking is what GUARANTEES bytes no input beat covers come out
    //      as 0 in the final strobe, instead of carrying stale bits
    //      forward. It's a correctness safety net, not a re-derivation
    //      of the address.
    assign masked_strb = up_w_strb & cur_mask;
    always_comb
        for (int b = 0; b < OUT_BYTES; b++)
            masked_data[b*8 +: 8] = cur_mask[b] ? up_w_data[b*8 +: 8] : 8'h0;

    // =========================================================
    // PUSH / POP handshake -- the part most likely to get poked at
    // =========================================================

    // Accept a new AW only once the current one has been dispatched.
    // A real design would also gate this on an input FIFO not being
    // full -- omitted here to keep focus on the repack control logic.
    assign up_aw_ready = (state == ST_IDLE);

    // Pop (accept) an upstream beat whenever we can do something useful
    // with it THIS cycle:
    //   ST_PASS                     : only if downstream can accept it
    //   ST_ACCUM, not completing    : always -- it only updates the
    //                                 accumulator, never touches dn_*
    //   ST_ACCUM, completing a slot : only if downstream can accept the
    //                                 flush -- otherwise the merged beat
    //                                 would be lost
    // INTERVIEWER Q: what breaks if up_w_ready ignored beat_completes
    // and just always equalled dn_w_ready?
    //   -> every non-flushing beat would incorrectly wait on a
    //      downstream handshake it doesn't need, stalling accumulation
    //      for no reason.
    assign up_w_ready = (state == ST_PASS)                     ? dn_w_ready
                       : (state == ST_ACCUM && !beat_completes) ? 1'b1
                       : (state == ST_ACCUM &&  beat_completes) ? dn_w_ready
                       : 1'b0;

    // Only assert downstream valid when actually emitting an output beat.
    // INTERVIEWER Q: could this glitch -- go valid for a cycle, then back
    // to invalid before dn_w_ready shows up?
    //   -> no: it's a direct function of up_w_valid/beat_completes, and
    //      `state` holds steady whenever dn_w_ready is 0 (see state_n
    //      below), so whatever made valid=1 this cycle is still true
    //      next cycle too. See "Handshake discipline" above -- this is
    //      exactly the property that rule protects.
    assign dn_w_valid = (state == ST_PASS  && up_w_valid)
                      || (state == ST_ACCUM && up_w_valid && beat_completes);

    assign dn_w_data = (state == ST_PASS) ? up_w_data : (accum_data | masked_data);
    assign dn_w_strb = (state == ST_PASS) ? up_w_strb : (accum_strb | masked_strb);
    assign dn_w_last = dn_w_valid && (out_beat_idx == last_slot_r);

    // =========================================================
    // Precompute: built once when an AW is accepted
    // =========================================================
    always_ff @(posedge clk) begin
        if (up_aw_valid && up_aw_ready) begin
            automatic logic [OFF_W-1:0] off = '0;
            // Safe to take the low LANE_W bits of up_aw_bytes_per_beat
            // here: a value of exactly OUT_BYTES (32) only occurs for a
            // pass-through transfer, which never reaches ST_ACCUM / this
            // precompute path at all.
            automatic logic [LANE_W-1:0] bpb = up_aw_bytes_per_beat[LANE_W-1:0];

            for (int k = 0; k < MAX_BEATS; k++) begin
                slot_tbl[k] <= off[OFF_W-1:LANE_W];
                if (k == up_aw_len) last_slot_r <= off[OFF_W-1:LANE_W];
                // INTERVIEWER Q: why capture last_slot_r here instead of
                // just reading slot_tbl[up_aw_len] after the loop?
                //   -> slot_tbl is written with non-blocking assignments;
                //      reading it back in the SAME always_ff would still
                //      see last cycle's value, not what this loop just
                //      computed. Capture it from the loop-local variable
                //      instead.

                // BIT-WIDTH NOTE: lane_end below must be LANE_W+1 bits
                // (0..32, not 0..31) -- lane_start + bpb reaches exactly
                // OUT_BYTES whenever a beat ends flush on a slot's top
                // edge. A LANE_W-bit lane_end wraps 32 to 0 here and
                // silently zeroes the whole mask. See "A real bit-width
                // bug" above -- this is that exact bug, fixed.
                automatic logic [LANE_W-1:0] lane_start = off[LANE_W-1:0];
                automatic logic [LANE_W:0]   lane_end   = {1'b0, lane_start} + {1'b0, bpb};
                for (int b = 0; b < OUT_BYTES; b++)
                    mask_tbl[k][b] <= (b >= lane_start) && (b < lane_end);

                off = off + bpb;   // one add per beat, not k * bpb
            end
            num_beats_r <= {1'b0, up_aw_len} + 1'b1;
        end
    end

    // =========================================================
    // FSM
    // =========================================================
    always_comb begin
        state_n = state;
        case (state)
            ST_IDLE:
                if (up_aw_valid && up_aw_ready)
                    state_n = (up_aw_bytes_per_beat == OUT_BYTES) ? ST_PASS : ST_ACCUM;
            ST_ACCUM:
                if (up_w_valid && up_w_ready && is_last_in_beat)
                    state_n = ST_IDLE;
                    // The real design also tries a same-cycle dispatch of
                    // the NEXT transaction's AW right here instead of
                    // always returning to IDLE -- omitted for brevity,
                    // see "Back-to-back dispatch" above.
            ST_PASS:
                if (up_w_valid && up_w_ready && up_w_last)
                    state_n = ST_IDLE;
            default: state_n = ST_IDLE;
        endcase
    end

    always_ff @(posedge clk) begin
        if (!rst_n) state <= ST_IDLE;
        else        state <= state_n;
    end

    always_ff @(posedge clk) begin
        if (!rst_n) begin
            beat_cnt     <= '0;
            out_beat_idx <= '0;
            accum_data   <= '0;
            accum_strb   <= '0;
        end else if (up_aw_valid && up_aw_ready) begin
            // New transaction accepted: every per-transaction counter
            // and the accumulator reset together, in the SAME cycle the
            // new AW lands.
            beat_cnt     <= '0;
            out_beat_idx <= '0;
            accum_data   <= '0;
            accum_strb   <= '0;
        end else if (up_w_valid && up_w_ready) begin
            beat_cnt <= beat_cnt + 1'b1;
            if (state == ST_ACCUM) begin
                if (beat_completes) begin
                    accum_data   <= '0;
                    accum_strb   <= '0;
                    out_beat_idx <= out_beat_idx + 1'b1;
                end else begin
                    accum_data <= accum_data | masked_data;
                    accum_strb <= accum_strb | masked_strb;
                end
            end else begin // ST_PASS
                out_beat_idx <= out_beat_idx + 1'b1;
            end
        end
    end

endmodule

Cheat sheet

The pattern

  • Narrow-to-wide write combining: one wide accumulator (data + strobe), mask each incoming beat to its legal byte lanes, OR-merge, flush on a slot boundary or last beat.
  • Slot = cumulative byte offset >> log2(output width) — a shift, not a divide, because the output width is a power of two.
  • If an operation (like a per-beat slot/mask calculation) is constant across a whole burst, computing it once at dispatch time and reducing the hot path to a table lookup is often cheaper than pipelining it.
  • One shared accumulator is only safe because of an upstream ordering guarantee (strictly increasing addresses) — note explicitly which protocol guarantee a simplification like this depends on.
  • Bit-width bug class: any add/concat of a boundary value (here, lane_start + bytes_per_beat reaching exactly the output width) needs the "+1 bit" headroom rule — check the true maximum of every intermediate signal, not just the ones that look wide.
  • Handshake-safe buffering: gate the ready you give your producer on your own output FIFO's fullness; never retract your own valid because of what's happening downstream.
  • Fast-path the common case (already-wide writes) separately from the general case, so simple traffic doesn't pay for machinery it doesn't need.
  • Check for an opportunity to dispatch the next transaction's address phase in the same cycle as the current one's last beat, rather than guaranteeing a bubble at every transaction boundary.

Takeaways

  • A bus-width mismatch between two stages doesn't need a multiply or a divide at all if you exploit what's actually constant within a transaction — here, bytes-per-beat is fixed per burst, so the arithmetic collapses to one small table, built once, not recomputed every cycle.
  • Exploiting a protocol guarantee (strictly increasing beat order) can replace a general, expensive structure (a multi-slot scoreboard) with a trivially cheap one (one accumulator) — but that saving is only as solid as the guarantee it rests on.
  • Off-by-one bit-width bugs hide at exact boundary values that ordinary testing tends to miss (here: a beat that lands exactly on a slot's upper edge) — the fix is always the same addition rule: check the true maximum value an intermediate signal can reach, not just how wide it "looks like it should be."
  • A valid/ready handshake has exactly one correct place to apply backpressure: the ready you hand your own producer. Never retract your own valid because something further downstream is stalled.
  • Fast-pathing the simple case (pass-through) and shaving a cycle off the common transition (back-to-back dispatch) are both small, local optimizations — and both pay off precisely because they target the traffic pattern that shows up most often in practice.
