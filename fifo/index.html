Logic Design Interview Prep/FIFOs

FIFOs: full explanation, from gates to gotchas

A FIFO looks trivial — "a queue in hardware" — right up until someone asks what happens when you try to write and read on the exact same clock edge, while the buffer happens to be full. That one question, worked all the way through, is most of what an interviewer actually wants to hear. This page builds the whole thing up from why it exists to a full implementation, with every edge case named explicitly.

What a FIFO is

First In, First Out: items come out in exactly the order they went in. One side pushes data in, the other side pops data out, and the FIFO itself never reorders anything.

Why it's needed

Two blocks that need to exchange data almost never produce and consume at identical, perfectly steady rates. A producer might burst several items in back-to-back cycles and then go idle; a consumer might process at a fixed cadence, or stall occasionally for its own reasons. Without a buffer in between, either side has to stop dead the instant the other can't keep up — a FIFO absorbs that mismatch, letting each side run at its own pace as long as the average rates agree over time.

A FIFO doesn't fix a permanent rate mismatch — if the producer is faster than the consumer forever, the FIFO just delays the inevitable overflow. What it buys you is tolerance for bursts and temporary stalls on either side.

Anatomy of a FIFO

Under the hood: a storage array (registers or RAM), a write pointer marking the next free slot, a read pointer marking the oldest occupied slot, and control logic that derives full/empty from those two pointers. It's a circular buffer — when a pointer reaches the last slot, it wraps back to slot 0.

Push and pop conditions

The baseline rule, before any edge cases: a push is only allowed when there's room, and a pop is only allowed when there's something there.

push happens when:  wr_en  &&  !full
pop  happens when:  rd_en  &&  !empty

Simple to state. The entire rest of this page is about what "full" and "empty" actually mean, and what happens at the exact moment one of them is about to change.

The classic problem: full and empty look identical

Use plain N-bit pointers that just wrap at the buffer depth, and watch what happens to a depth-4 FIFO:

Statewr_ptrrd_ptrEqual?
Freshly reset, nothing written0000yes
Pushed 4 items (completely full), none read00 (wrapped back around)00yes

Both states give wr_ptr == rd_ptr. With only N bits of pointer, empty and completely-full are indistinguishable — comparing the pointers alone cannot tell them apart.

The standard fix: one extra pointer bit

Make the pointers one bit wider than needed to address the memory. For a depth-D (power of two) FIFO needing N=log₂D address bits, use N+1-bit pointers. The low N bits still address the memory; the extra top bit flips every time a pointer wraps around. Two pointers can now be equal in address but differ in that top bit — and that difference is exactly what separates "empty" from "full."

Fullyesno — differentwrite has lapped read exactly once

Worked through on the same depth-4 example, with 3-bit pointers (2 address bits + 1 extra):

Exactly the behavior needed, with nothing more exotic than one extra flop per pointer. Bonus: wr_ptr − rd_ptr (as unsigned (N+1)-bit subtraction) directly gives the current occupancy count, 0 through D, thanks to the pointers living in mod-2N+1 arithmetic while the buffer itself is exactly 2N deep.

Alternative: an explicit counter

Instead of comparing pointer bits, keep a separate up/down counter that directly tracks occupancy: increment on a push-only cycle, decrement on a pop-only cycle, hold on both-or-neither. full = (count==DEPTH), empty = (count==0).

Pointer-compare

No adder/subtractor needed for full/empty — just a bit compare. Naturally gives you the count too, almost for free, via subtraction. The standard choice in most FIFO IP.

Explicit counter

Conceptually simpler to read in RTL, and doesn't require the depth to be a clean power of two to reason about — but needs a real up/down counter (an extra adder/subtractor), and simultaneous push+pop must be handled as one explicit case (hold), not accidentally coded as sequential if/else priority that only applies one of the two.

Simultaneous read and write — the part interviewers actually probe

The normal case: neither full nor empty

Nothing special: the push and the pop both happen, occupancy stays the same, both pointers advance by one. No interaction between them at all.

Read and write together while FULL

This is the one most naive implementations get wrong. If "full" is used to flatly block every write, a simultaneous pop-and-push on a full buffer loses the incoming item for no reason — the pop just freed a slot in that same cycle, so the push should be allowed to land in it, keeping the FIFO at full occupancy with one item correctly swapped for another.

wr_act = wr_en && (!full || rd_act)     // let the write through if a same-cycle pop frees room
rd_act = rd_en && !empty

Read and write together while EMPTY

This one is not automatically safe, and the asymmetry with the full case is itself a good interview point. A write landing this cycle doesn't exist in memory until the clock edge completes — there is nothing yet for a same-cycle read to fetch. Without extra hardware, rd_act must stay strictly rd_en && !empty: a read request against an empty FIFO is simply held off, even if a write is happening in that same cycle, and the data becomes poppable starting next cycle. Making the just-written data visible in the same cycle it arrives needs an explicit bypass path — which is precisely what the next section is about.

First-Word Fall-Through (FWFT) vs. standard output

Standard (registered output)

Assert rd_en for one cycle to request a pop; the data appears on rd_data one cycle later. The consumer has to remember "I asked, I'll see it next cycle."

FWFT

rd_data continuously shows the current head item whenever !empty, with no request needed to see it. rd_en (often called pop or an accept/ack signal in this mode) just means "I'm done with this one, advance." One cycle of latency saved on every pop.

cycle1234
standard: rd_en1000
standard: rd_data validyes
FWFT: rd_data validyes (already)
FWFT: rd_en (accept)1000

The classic integration bug: treating a FWFT FIFO's rd_en as "give me new data" — which silently skips the item currently sitting on rd_data, since it was already valid before you ever asserted anything. Or the mirror mistake: treating a standard FIFO's rd_en as "the data is already there," reading one cycle too early and getting stale data. Always check which convention a given FIFO (your own, or a vendor IP core) actually implements before wiring up the consumer — it's a one-line datasheet detail with an easy-to-miss, hard-to-debug consequence.

Overflow, underflow, and watermark flags

Two more flag conventions worth naming explicitly:

Overflow / underflow (sticky error flags)

Internally, a push while full or a pop while empty must always be silently discarded by the FIFO itself — pointers must never be corrupted by an illegal request. Whether to also raise a sticky overflow/underflow flag for the system to notice is a separate design choice: it turns a silent, easy-to-miss bug in the producer/consumer into a visible, debuggable one.

Almost-full / almost-empty (programmable watermarks)

A producer that only finds out the FIFO is full the same cycle it tries to write may already be one cycle too late if there's any round-trip latency in the handshake. An almost_full flag, asserted some programmable number of slots before actually full, gives the producer enough warning to stop in time — the exact margin needed is a direct function of that round-trip latency.

A full implementation

Parameterized, pointer-compare style, with the simultaneous-read/write handling from above built in and every push/pop condition commented.

module sync_fifo #(
    parameter int WIDTH = 8,
    parameter int DEPTH = 16          // MAGIC NUMBER: must be a power of 2 -- the
                                       // extra-bit trick below depends on it exactly
) (
    input  logic             clk,
    input  logic             rst_n,    // active-low, synchronous

    input  logic             wr_en,
    input  logic [WIDTH-1:0] wr_data,
    output logic             full,

    input  logic             rd_en,
    output logic [WIDTH-1:0] rd_data,
    output logic             empty
);

    localparam int AW = $clog2(DEPTH);   // address bits into the memory

    logic [WIDTH-1:0] mem [DEPTH];
    logic [AW:0] wr_ptr, rd_ptr;         // AW+1 bits -- the extra top bit IS the trick

    // =====================================================
    // PUSH / POP qualification -- the part most likely to get poked at
    // =====================================================
    logic wr_act, rd_act;
    assign rd_act = rd_en && !empty;
    // INTERVIEWER Q: why does wr_act check rd_act, but rd_act doesn't
    // check wr_act back?
    //   -> a same-cycle pop always safely frees a slot for a write (see
    //      "Simultaneous read and write, FULL" above); a same-cycle
    //      write does NOT make data available to a same-cycle read
    //      without extra bypass hardware (see "FWFT" above) -- the two
    //      directions are genuinely not symmetric.
    assign wr_act = wr_en && (!full || rd_act);

    always_ff @(posedge clk) begin
        if (wr_act) mem[wr_ptr[AW-1:0]] <= wr_data;
    end
    assign rd_data = mem[rd_ptr[AW-1:0]];
    // INTERVIEWER Q: when FULL and both acts fire, wr_ptr and rd_ptr
    // address the SAME slot this cycle -- is rd_data still correct?
    //   -> yes: mem[] only updates via a non-blocking assignment, which
    //      takes effect at the end of this time step, so the
    //      combinational read above still returns the OLD value this
    //      cycle. The new value is visible starting next cycle, after
    //      rd_ptr has already moved past this slot.

    always_ff @(posedge clk) begin
        if (!rst_n) begin
            wr_ptr <= '0;
            rd_ptr <= '0;
        end else begin
            if (wr_act) wr_ptr <= wr_ptr + 1'b1;   // wraps naturally at 2^(AW+1)
            if (rd_act) rd_ptr <= rd_ptr + 1'b1;
        end
    end

    // The extra-bit trick:
    //   empty: pointers fully equal, including the extra top bit
    //   full : same address (low AW bits), extra bit differs --
    //          write has lapped read exactly once
    assign empty = (wr_ptr == rd_ptr);
    assign full  = (wr_ptr[AW-1:0] == rd_ptr[AW-1:0]) && (wr_ptr[AW] != rd_ptr[AW]);
    // INTERVIEWER Q: could full and empty ever both be true at once?
    //   -> no, by construction: empty requires the top bits to match;
    //      full requires them to differ. Mutually exclusive, always.

endmodule
Illustrative, simplified for teaching — a real design would also reset/guard mem[] contents predictably for simulation and may register rd_data for timing depending on whether standard or FWFT behavior is wanted (this version is effectively FWFT, since rd_data is a combinational read that's valid the instant !empty, with no separate request needed).

Related data structures

LIFO / stack

Push and pop happen at the same end (the top), tracked by a single pointer — not two. "What's the structural difference between a FIFO and a LIFO" is a fair, simple interview question whose honest answer is exactly that: one pointer and one end, versus two pointers and two ends.

Shift-register FIFO

For very shallow depths, some designs literally shift every entry one slot over each cycle instead of moving pointers — no address logic at all, at the cost of every stored bit toggling every cycle. This is the exact same flops-vs-RAM-circular-buffer trade-off covered in depth on the Sliding Window page's moving-average section — same trade-off, same crossover reasoning, different application.

Asynchronous (dual-clock) FIFO

When the write side and read side run off unrelated clocks, comparing raw binary pointers across the boundary is unsafe — incrementing a binary counter can flip several bits at once (e.g. 011→100), and a sampler on the other clock could catch an inconsistent mix of old and new bits. The fix is Gray-coded pointers, where consecutive values differ in exactly one bit, so an asynchronous sample is always either the fully-old or fully-new value, never garbage. The full cross-domain synchronizer-chain treatment lives on this site's CDC & synchronizers page — this is the FIFO-specific reason it's needed.

Monotonic deque

Looks superficially similar (a double-ended buffer), but solves a completely different problem — maintaining a running maximum, not preserving arrival order. Covered in full, with traces, on the Sliding Window page. A good reminder that "queue-shaped" doesn't mean "FIFO-shaped": a FIFO never reorders or discards entries the way a monotonic deque deliberately does.

Gotchas

"Just gate write_en with !full and read_en with !empty, done."
Not quite — that naive version loses data on a simultaneous push+pop while full, since it blocks the write even though the concurrent pop just freed a slot. See "Simultaneous read and write" above.

"If it's safe to write-through on full, it must be symmetric for empty."
It isn't. A same-cycle pop safely reuses a slot being read; a same-cycle push doesn't make data available to a same-cycle read without explicit bypass hardware (FWFT-style). Two different mechanisms, not mirror images.

"The depth doesn't need to be a power of two."
Not for the extra-bit trick — it specifically relies on the pointer wrapping at exactly 2× the addressable depth. A non-power-of-two depth needs explicit magnitude comparison logic instead of the simple bit-compare.

"FWFT and standard-output FIFOs use read_en the same way."
They don't — FWFT's rd_en means "accept/advance," standard's means "request." Mixing the two conventions up when integrating a vendor IP core is a classic, easy-to-miss bug.

"A pointer that's one bit too narrow just wraps around harmlessly."
It silently breaks full/empty detection — the exact same "+1 bit of headroom" rule covered on the Flip-Flops and CBUSY pages applies here: check the true range a signal needs, not what looks wide enough.

Interview Q&A

Interviewer: Design a FIFO. What do you need to track?

You: A storage array, a write pointer to the next free slot, a read pointer to the oldest item, and full/empty flags derived from comparing them.

Interviewer: If you just compare the pointers directly, what goes wrong?

You: Full and empty both show up as the pointers being equal — with plain N-bit wrapping pointers there's no way to tell them apart.

Interviewer: How do you fix that?

You: Widen the pointers by one bit beyond what's needed to address the memory. Empty is the pointers fully equal, including that extra bit; full is the address bits equal but the extra bit different — meaning write has lapped read exactly once.

Interviewer: Now: what happens if I assert write and read on the same cycle, and the FIFO is completely full?

You: It should stay full, correctly — the pop frees the slot the push needs in that same cycle. If the write is unconditionally blocked whenever full is asserted, that incoming write is lost for no reason. The fix is to allow the write through whenever a same-cycle read is also happening.

Interviewer: Doesn't that mean the read and write hit the exact same memory address in the same cycle? Is that safe?

You: Yes to both. When full, the write and read pointers address the same physical slot by construction. It's safe because the memory write is non-blocking — it doesn't take effect until the end of the clock edge, so the read sees the old data this cycle regardless, and the new data only becomes visible next cycle.

Interviewer: Same question, but now the FIFO is completely empty.

You: That one's not automatically safe the same way. The data being written this cycle doesn't exist in memory until the edge completes, so a same-cycle read has nothing to fetch yet — unless the design explicitly adds a bypass path to forward the write data straight to the read output. Without that bypass, the read just has to wait one more cycle, which is exactly the standard-output-FIFO behavior; with it, you've built the write-side half of a first-word-fall-through FIFO.

Cheat sheet

  • Push: wr_en && !full. Pop: rd_en && !empty — the baseline, before edge cases.
  • Full/empty ambiguity: plain N-bit pointers can't distinguish full from empty — both look like wr_ptr==rd_ptr.
  • Standard fix: (N+1)-bit pointers. Empty = fully equal (incl. top bit). Full = address bits equal, top bit differs.
  • Simultaneous R/W while FULL: safe and should be allowed — wr_act = wr_en && (!full || rd_act). Relies on non-blocking writes so same-cycle, same-address reads still see old data.
  • Simultaneous R/W while EMPTY: not symmetric — a read cannot see same-cycle write data without an explicit bypass (FWFT) path.
  • FWFT: data visible before any read request; rd_en means "advance," not "request." Standard: data appears one cycle after rd_en; means "request."
  • Depth must be a power of two for the extra-bit trick; otherwise use explicit magnitude comparison.
  • Async FIFO: needs Gray-coded pointers across the clock boundary — binary pointers can present a glitchy multi-bit value to an asynchronous sampler.
  • FIFO vs. LIFO: two pointers/two ends vs. one pointer/one end.
