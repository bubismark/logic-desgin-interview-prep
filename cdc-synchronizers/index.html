CDC & synchronizers

Two clock domains with no fixed phase relationship to each other is the normal state of a real chip, not an edge case. Every signal that crosses that boundary is an opportunity for a flip-flop to be asked to sample a value at the exact wrong instant — and the entire subject of this page is what happens then, and the handful of well-understood techniques that make it safe anyway.

Why crossing clock domains is dangerous

A clock domain is a region of logic whose flip-flops are all ultimately driven by the same clock, switching in a coordinated, predictable way relative to each other. The moment a signal crosses from one clock domain into a flip-flop in a different clock domain, every timing guarantee STA normally relies on — "this signal is stable for X ns before and after the edge" — is gone. The two clocks have no fixed relationship; the crossing signal can change at any instant relative to the receiving flop's clock edge, including the one instant a flip-flop can't tolerate: inside its own setup/hold window. The Flip-Flops page on this site covers what setup and hold time actually guarantee — this page is entirely about what happens the moment that guarantee is broken, and how to make that safe anyway.

Metastability, and the MTBF formula

A flip-flop is a bistable element: it's built to settle into one of exactly two stable states. Violate setup or hold — feed it an input that changes too close to the clock edge — and for a little while, the internal node can sit between those two states: not a valid 0, not a valid 1, just an indeterminate voltage. This is metastability. Eventually, random tiny imbalances inside the gate push it to one side or the other — but "eventually" is the key word: the time that takes is not fixed, and in principle is unbounded.

The probability that metastability lasts longer than some resolution time t_r falls off exponentially with t_r. That gives the standard reliability figure for a synchronizer, Mean Time Between Failures:

MTBF  =  e(t_r / τ)  /  (T0 × f_clk × f_data)
  • t_r — the resolution time you give it: roughly one extra clock period per extra synchronizer stage.
  • τ (tau) — a technology-specific time constant of the flip-flop itself: how fast it tends to resolve out of the indeterminate zone. Smaller is better, and it's a cell-library property, not something you can design around in RTL.
  • T0 — another technology constant, related to how wide the input window is that can actually trigger metastability.
  • f_clk, f_data — the sampling clock frequency and how often the asynchronous input changes. More attempts per second, more opportunities to land in the danger window.
The one thing worth taking away from this formula: MTBF scales as et_r/τ — exponentially in the resolution time. Illustrative numbers: a technology with τ=200 ps, given just one extra 2 ns clock period of resolution time, improves MTBF by a factor of e(2ns/0.2ns) = e10 ≈ 22,000×. (τ and T0 are real, measured, library-specific numbers in an actual design — these are illustrative, not universal constants.) That's the entire mathematical justification for why adding one more flip-flop stage to a synchronizer is such an enormous reliability win for such a small cost.

The 2-flop synchronizer

A single flip-flop sampling an asynchronous signal gives that signal exactly zero dedicated resolution time — if it goes metastable, that bad value (or an eventual-but-late resolution) feeds straight into downstream logic. The standard fix: add a second flip-flop, clocked by the same destination clock, sitting between the first flop and the rest of the logic.

module sync2ff (
    input  logic clk_dst,
    input  logic rst_n,
    input  logic async_in,
    output logic sync_out
);
    logic ff1;   // INTERVIEWER Q: why no reset-value guarantee claimed for ff1?
                 //   -> it's explicitly allowed to be metastable for a while;
                 //      the circuit's correctness depends on FF2, not on FF1
                 //      ever holding a "clean" value at every instant.
    always_ff @(posedge clk_dst) begin
        if (!rst_n) begin
            ff1      <= 1'b0;
            sync_out <= 1'b0;
        end else begin
            ff1      <= async_in;
            sync_out <= ff1;
        end
    end
endmodule

When 2 isn't enough

Two stages is the common default, but the MTBF formula says exactly when it stops being sufficient: at very high clock frequencies (less resolution time per stage) or for very high-reliability requirements (automotive, aerospace, safety-critical designs), the MTBF from 2 stages can fall below what's acceptable. The fix is mechanical — add a third flip-flop, same clock, same chain — and the payoff is the same exponential jump described above, applied once more.

The narrow-pulse problem

Everything above assumes the signal being synchronized is a level that stays stable for a while. A pulse is different: if it's narrower than roughly one destination clock period, it can fall entirely between two consecutive sampling edges and never get captured at all — not metastably, just completely invisible.

The standard fix converts the unreliable pulse into a reliable level before it ever gets near a synchronizer: toggle a flip-flop in the source domain every time the pulse fires. A toggle is a level change that persists until the next pulse — exactly the kind of signal the plain 2-flop synchronizer handles safely. The destination domain then edge-detects the synchronized toggle to regenerate a clean, one-cycle pulse of its own.

// Source domain: turn an unreliable pulse into a reliable level
always_ff @(posedge clk_src) begin
    if (!rst_n)        toggle_src <= 1'b0;
    else if (pulse_in) toggle_src <= ~toggle_src;
end

// 2-flop synchronizer, into the destination domain
logic sync1, sync2;
always_ff @(posedge clk_dst) begin
    if (!rst_n) begin
        sync1 <= 1'b0;
        sync2 <= 1'b0;
    end else begin
        sync1 <= toggle_src;
        sync2 <= sync1;
    end
end

// Destination domain: edge-detect to regenerate a clean, 1-cycle pulse
logic sync2_prev;
always_ff @(posedge clk_dst) begin
    if (!rst_n) sync2_prev <= 1'b0;
    else        sync2_prev <= sync2;
end
assign pulse_out = sync2 ^ sync2_prev;

Why multi-bit buses can't just use N independent synchronizers

Put a 2-flop synchronizer on every bit of a bus independently, and each bit is individually protected from metastability. That's not enough. Different bits can have slightly different physical delays, so when several bits of a bus change at once in the source domain, there's no guarantee the destination domain's sampling instant lands cleanly before or after all of them — it can land after some and before others, capturing a value that was never valid in either domain.

Concrete, classic example: a counter going from binary 0111 (7) to 1000 (8) changes all four bits at once. If a destination flop samples mid-transition and happens to catch some bits already updated and others not yet, the captured value could be almost anything — including, say, 1111 (15) or 0000 (0), neither of which the counter ever actually held. This is exactly why counters/pointers crossing a clock domain (like a FIFO's read/write pointers) need more than "just synchronize every bit."

Gray-coded pointers

The fix for counters and pointers: encode the value so that only one bit ever changes between consecutive values. Then a destination sample mid-transition can only ever catch the fully-old value or the fully-new value — there is no other bit to be caught halfway, so there's no invalid combination to land on.

// Binary to Gray: trivial, one XOR per bit
assign gray = binary ^ (binary >> 1);

// Gray to binary: each bit depends on the (already-recovered) bit above it
always_comb begin
    binary[WIDTH-1] = gray[WIDTH-1];
    for (int i = WIDTH-2; i >= 0; i--)
        binary[i] = binary[i+1] ^ gray[i];
end

Verified for every 3-bit value: binary 0..7 → Gray 000, 001, 011, 010, 110, 111, 101, 100 → converted back through the gray-to-binary logic above recovers 0..7 exactly, with no mismatches. This is the standard, well-known reflected binary Gray code — worth confirming by hand once rather than trusting it from memory.

Handshake CDC for arbitrary wide data

Gray coding only works for values that change by exactly one count at a time — a counter or pointer. For an arbitrary data word that can change to any new value at once, the standard technique is a request/acknowledge handshake instead.

1

Source drives data, then asserts req

The data bus is set up first and held stable — it must not change again until the source sees the acknowledgment, since the destination might sample it at any point after req is recognized.

2

req crosses via a 2-flop synchronizer

Now a clean level in the destination domain's own clock.

3

Destination captures data, asserts ack

Only now, once req is safely recognized, is the data latched.

4

ack crosses back via its own 2-flop synchronizer

The source only releases/changes data once it sees the synchronized ack.

Correct and general, but slow: a full round trip costs several cycles in both domains, just for two synchronizer crossings. For a continuous stream of wide data, this throughput cost is exactly why the next section's approach is preferred instead.

Tying it together: the asynchronous FIFO

The standard high-throughput answer for streaming data between clock domains combines everything above: Gray-coded pointers (safe to cross), a 2-flop synchronizer for each pointer (in each direction), and the dual-port memory array itself from the FIFO page — each location is only ever written by one domain and read by the other, with the pointers' own synchronization being what keeps that safe.

The one genuinely tricky piece: comparing Gray-coded pointers for full isn't a simple equality check the way empty is. Empty is just rd_ptr_gray == wr_ptr_gray_sync (Gray code is a one-to-one mapping, so equality in Gray means equality in the underlying count, same as the synchronous FIFO's binary-pointer case). Full needs the write domain to recognize "the read pointer, converted back to what it would mean in my own numbering, is exactly one full wrap behind me" — which works out to a specific bit-flip rule:

// full, checked in the WRITE domain, AW = address width (pointers are AW+1 bits)
assign full = (wr_ptr_gray == {~rd_ptr_gray_sync[AW:AW-1], rd_ptr_gray_sync[AW-2:0]});

Gotchas

"A setup/hold violation just gives you the old or new value, pick one."
It gives you an indeterminate, unpredictably-timed resolution — metastability, not a clean binary choice. That unpredictable duration is the entire reason synchronizers need dedicated resolution time, not just "a flop for good luck."

"Put some combinational logic in front of the first synchronizer flop, it's just a few gates."
Don't — the first flop of a synchronizer chain must be driven directly by the raw asynchronous signal. Combinational logic in front of it defeats the whole point: now there isn't one well-understood metastability-prone node, there's a gate network whose own glitch behavior isn't part of the analysis at all.

"Synchronize the signal once, then fan it out everywhere it's needed."
Only if it's genuinely one signal — synchronizing two related signals through two independent synchronizer instances can let them resolve on different cycles, so downstream logic can briefly see an inconsistent combination (a "reconvergence" bug). Synchronize once, fan out the synchronized result — don't resynchronize the same information twice.

"STA will catch any CDC timing problem."
STA needs to be told not to try — the path into a synchronizer's first flop is deliberately, intentionally asynchronous, and without an explicit false-path (or equivalent) constraint, static timing analysis will report an endless stream of "violations" on a path that was never meant to meet normal setup/hold in the first place.

"A reset signal doesn't need its own synchronization."
If it originates in a different clock domain, it does — an asynchronously-asserted, asynchronously-released reset can itself violate the exact same setup/hold rules as any other cross-domain signal, with the same consequences.

Interview Q&A

Interviewer: Why can't you just connect an async signal straight into a flip-flop in another clock domain?

You: No fixed timing relationship between the two clocks means the signal can change at any instant relative to the receiving flop's edge, including inside its setup/hold window — which risks metastability: the flop's internal node can sit at an invalid voltage for an unpredictable amount of time before resolving.

Interviewer: How do you fix that?

You: A 2-flop synchronizer — a second flop, same destination clock, sitting after the first. If the first flop goes metastable, it gets a full clock period to resolve before the second flop samples it. MTBF scales exponentially with that resolution time, so even one extra stage is a massive reliability win.

Interviewer: When would two stages not be enough?

You: Very high destination clock frequencies, which give less resolution time per stage, or very high reliability requirements where the MTBF from two stages isn't good enough — a third stage buys another exponential jump.

Interviewer: Does this handle a narrow pulse the same way?

You: No — a pulse narrower than about one destination clock period can fall entirely between two sampling edges and be missed completely, not metastably, just invisibly. The fix is to toggle a flip-flop in the source domain on every pulse, turning it into a stable level, synchronize that level with the normal 2-flop technique, then edge-detect it in the destination domain to regenerate a clean pulse.

Interviewer: What about a multi-bit bus, like a counter value?

You: Independent per-bit synchronizers aren't enough — different bits can resolve on different cycles, and if several bits change at once in the source domain, a destination sample can catch a mixed, never-valid combination. For a counter or pointer, the fix is Gray coding: only one bit changes per step, so a sample mid-transition can only ever be the fully-old or fully-new value.

Interviewer: And for an arbitrary data word, not just a counter?

You: Gray coding doesn't apply there since the value can jump to anything, not just count by one. That needs a request/acknowledge handshake: data held stable, req synchronized across, destination captures and acks, ack synchronized back before the source changes data again. Slower than Gray-coded pointers — a full round trip costs several cycles in both domains — which is exactly why an async FIFO, built from Gray-coded pointers plus dual-port memory, is the standard choice when you need to stream wide data continuously instead.

Cheat sheet

  • Metastability: an indeterminate, unpredictably-timed resolution after a setup/hold violation — not just a wrong value.
  • MTBF ∝ et_r/τ — each added synchronizer stage buys another exponential jump in reliability.
  • 2-flop synchronizer: standard default for a single-bit level crossing a clock domain. 3-flop when frequency or reliability needs demand it.
  • Narrow pulses can be missed entirely by a plain synchronizer — convert to a toggle in the source domain, synchronize the toggle, edge-detect it in the destination domain.
  • Multi-bit buses need more than N independent synchronizers — use Gray coding for counters/pointers (only 1 bit changes per step) or a req/ack handshake for arbitrary data.
  • Gray-to-binary: binary[MSB]=gray[MSB], then binary[i] = binary[i+1] ^ gray[i] going down.
  • Async FIFO full (in Gray): wr_gray == {~rd_gray_sync[AW:AW-1], rd_gray_sync[AW-2:0]} — not a plain equality check.
  • Never put combinational logic in front of a synchronizer's first flop. Never resynchronize related signals independently. Always false-path the synchronizer's input in STA.
